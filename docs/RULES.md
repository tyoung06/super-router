# Super Router rules

Version 2.55 · 2026-11-05 · A cleaned copy of the owner's rules, made at each publish.

## What this project is

The owner types a task. Jev labels it with one skill. The skill table picks the agent that does the work
and the agent that checks it. Or the owner names a preset, and the task runs as a chain of stages, one
agent per stage, with the last result checked by a named checker or by the chain's own last stage, or
with two results each reviewed by the other builder and the owner picking one, or with a result attacked
by two adversaries, each on its own, and revised before it is checked, or with three agents answering a question on their
own and the answer most of them reached taken as the result (see Relay). The owner may fill a preset's slots with other
agents than its defaults for one task (see Slots, under Relay). Or the owner splits a task: a planner breaks
it into pieces the owner approves, each piece runs as its own task with the team the plan gives it, and an integrator joins the
results (see Split). A call that stops (an error, a plan limit, or Grok still out when overdue) is taken over
once by the next agent, by the router itself (see Takeover); a process that ended is resumed by hand (see
Resume). Every agent but Claude is optional: one that isn't available is stood in for by the next (see Availability). A task whose result failed its check twice can be redone
once by its checker, with the original doer checking (see Fallback). A task may belong to one of
the owner's projects; then the agents get that project's handoff file and the result feeds it back (see
Project context). Or a task is tagged with a chat name, and the agents get what the router remembers under that
tag: earlier results, stored in a local memory store and searched in code, with nothing for a model to maintain (see Memory). A project task gets the same memory under its project's tag, beside its handoff file. Every task goes in one log, and a status page shows the agents. A local page, the
interface, shows the log and runs the same commands with buttons (see Interface); after a result it suggests the next move, which the owner sends themselves (see Next steps), and on a project it makes a plan the owner approves, then builds it a step at a time, by hand or with Auto (see The plan and Auto); which model each agent uses is their to choose (see Models). A pixel office
comes later, driven by the same log. A public copy of the code, the tests, the demo and the docs is published from this repo (see Public copy).

Version 1 routed between a Claude worker and Grok Bot. Version 2 adds Jev as the labeler, a checker,
ChatGPT, media (a task can carry a file, and Grok can make an image), relay chains, resume, web
search for Claude and ChatGPT on every call (see Web search), versus, fallback, split, project context, the
interface, slots, redteam, vote, memory (Hindsight, with chats as its tag), and Cursor as a coding agent on the X Subscription (see Cursor). Muse is deferred and its skills are reassigned (see Agents in v2).

Version 1 is retired as of 2026-10-08. Its code is the starting point for version 2. It is no longer
used or improved on its own, and none of its bars or deadlines apply.

## Hard rules

1. **Plan first.** Present a written plan and wait for approval before any multi-step work. Once approved, run it end to end without checking back.
2. **Tests before code.** A step is not done until a test covers it and passes.
3. **One commit per working step**, with a clear message.
4. **NOTES.md updated every step:** where we are, open issues, next 3 steps.
5. **Teach as you go.** After each non-trivial change, a 1–2 line "Why".
6. **Flag every guess.** Label claims `[VERIFIED]`, `[FROM MEMORY]`, or `[GUESS]`.
7. **Stuck after 2–3 attempts on one error: stop.** Show the error, what was tried, and the best theory.
8. **Stay on task.** Anything else noticed gets one line in NOTES.md, not a fix.
9. **Boring stack.** Python for the router. Plain JS only for a page. No new dependency without a one-line reason.
10. **The log is the truth.** Code writes every log row. A model never writes status, IDs or timestamps.
11. **Answer keys come first.** In any test of a model, the right answers are fixed before the model runs. A label changed after seeing a model's answer does not count.
12. **One agent at a time.** A new agent is switched on only after the one before it passed its send test and its return test with no clicks, and handled 3 real tasks.

## Secrets (strict)

- Keys live in `.env` only. `.env` is in `.gitignore`.
- Never print, log, commit, or paste a key or the webhook URL. Not in code, NOTES.md, test output, or chat.
- Every result is passed through the redactor before it is stored or shown.
- The redactor masks every `.env` value of 8 characters or more, not only the named keys, wherever text is stored or shown: the log, the prose, the JSON and the round files. A shorter value is not treated as a secret and is never masked (a value like `1` would mask every `1`). The task text is redacted at intake, before Jev and before its row; a file whose name holds a `.env` value is refused at intake. Built by briefs 21 and 22.
- A key seen anywhere else: stop and flag it before doing anything more.
- Tests use fake values only.
- The only model API key allowed is `JEV_API_KEY`.
- A project's handoff file is passed through the redactor before it is sent to any agent. A handoff that still holds something that looks like a key after redaction is not sent: the task comes back to the owner with the line number.
- The router notes, a project's notes and its `SPEC.md` are checked on every save for a `.env` value and for anything that looks like a key, and refused naming the line, never the value; the router notes and the spec are checked again at intake, and the router notes before each send (see Router notes, The spec).
- A memory is stored from text that already went through the redactor, and a recalled memory goes through the redactor again before it is sent (see Memory). The memory store listens on the loopback address only, holds no key and is given none. A recalled memory that still looks like it holds a key is dropped from the block and the call row names its task number; the task is not stopped for it.
- Cursor is reached through its own login (`agent login`), kept by Cursor in its own folder, never through `CURSOR_API_KEY`: the variable is never set and never put in `.env`, and the router refuses to run while it is set (see Money). Cursor's result goes through the redactor like every result, and `key_like` runs on everything handed to it (see Cursor).
- A project's `.env` is written only by `sr project secrets` (brief 31): the value on stdin, never in an argument list, a log row, JSON or the page; mode 600; never the router's own `.env`. A run's output is redacted with the router's `.env` values and the project's before it is written or shown (see Test, Run and Secrets).
- The interface listens on the loopback address only, never on a network interface, and has no login because nothing but this Mac can reach it. Everything it shows has been through the redactor. It never reads `.env`. A JSON command's output goes through the redactor before it is printed or served.

## Money

- New monthly spend allowed: $0, with one exception: Jev.
- **Jev runs on prepaid credit only.** Auto top-up stays off and no card is left on file for overage. The router never changes billing settings.
- **Jev cap, enforced in code:** the router stops calling Jev after 1,000,000 input tokens in a calendar month (UTC). That is about $0.04 at $0.042 per million. Past the cap, Jev is not called and the log says so. The Jev section says what happens to the task.
- The router refuses to run if any per-token billing switch is on: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `OPENAI_API_KEY`, `CODEX_API_KEY`, `CURSOR_API_KEY`, or an `apiKeyHelper` in Claude settings.
- Claude and ChatGPT are reached through plan logins only. When a plan limit is hit, the router hands the stopped call to the next agent once (see Takeover) and the log says so. Nothing is bought to keep going. A takeover is one extra call for the stopped call, at most, and then the task's usual calls; so is a manual resume (see Resume).
- A fallback costs the task's usual calls once more, at most: the redo (on a relay task with its stage's one contract re-ask), its check, one fix round and its re-check. The owner runs it; the router never starts one. One per task.
- A split costs one planning call, then each piece's calls as its team spends them (a routed piece's usual calls, or its preset's), then one integration call and its usual check loop. At most 4 pieces. The pieces run only after the owner approves the plan, which shows them each piece's team and agents and the router's count of the calls from there, with the most the fix rounds could add, so the owner sees the cost before it is spent. Jev labels each piece once at plan time, and a piece's new text once more.
- Project context costs no extra call. The handoff rides inside the task's usual calls; the handoff section of a result is part of the result, and the router, not a model, writes the handoff file. The one contract re-ask a handoff section may get is the task's usual re-ask, not an extra one.
- Next steps cost no model call (brief 33): the chips, What now? and the Ideas list are code, and an earlier result carried by `--from` rides inside the task's usual calls.
- A plan costs `redteam`'s calls (brief 33.1): the plan, one or two attacks, the revision, then the check and one fix round, 5 to 7 calls (4 to 6 with one attacker) plus any contract re-ask, shown before Send. The plan card counts every step's calls before the owner approves, and each step costs what its team costs when the owner sends it. Ticks, needs and What now? are code.
- Models (brief 33.3) never change how many calls a task makes, but Opus and Fable draw more of the Max plan's weekly limit, which the router shares with Claude Code's own builds. Fable is free only up to half that limit; past it, it charges usage credits, which Claude Code's `-p` mode pays without asking, and the router can't see whether usage credits are on. So Fable is off in the router until the owner turns it on, which is their confirmation that usage credits are off on their account. A cost figure in a stream on a plan login is an estimate, never a charge (see Models).
- An Auto run (brief 34) spends what its steps spend, and stops at its budget: the plan card's upper call estimate for its steps plus 50%. A step already started finishes, so a run can pass its budget by up to one step's calls (see Auto).
- Memory costs no model call and no money. Hindsight runs on this Mac with no LLM provider and no API key; storing and searching are local. The memory block rides inside the task's usual calls. The store is never a subscription: Hindsight Cloud is not used.
- The interface and `sr status` cost no model call. An agent's online check is never a prompt to a model: Claude's is `claude auth status` answering that it is signed in with the plan (`authMethod` `claude.ai`), ChatGPT's is the `codex` command answering that it is signed in, Cursor's is the `agent status` command answering the same, Grok's is the inbox repo answering. The webhook is never called by a check. A check that doesn't answer is run once more, still with no model call (see Availability). A task started from the interface costs exactly what the same `sr` command costs in Terminal.
- Claude's web search runs on the plan login like the rest of the call. No search API, no search key, no paid search.
- A probe the router runs on its own (see Web search and Cursor) costs 2 Claude calls on the plan for Claude's half and 3 Cursor calls from the pool for Cursor's, and runs only when that tool's installed version has no pass and no failure on record (one that could not run is tried at most once an hour): a few times a month at the rate the tools update themselves. Starting and backfilling memory cost no model call. ChatGPT's own probe (the Codex sandbox check) is one ChatGPT call per Codex version, run by the router before ChatGPT's first call on a new version (brief 24).
- Searching on every call uses more of each plan and makes calls slower. The owner accepted both on 15 Oct. When a plan runs out, the task stops on its plan limit as any call does (see Resume); nothing is bought.
- Grok Bot on-demand spend stays off. Muse stays on its free plan.
- Cursor runs on the X Subscription's included weekly pool, the pool Grok Bot and the Grok apps already draw from, and on nothing else: the prepaid balance stays at $0 and auto top-up stays off, so nothing can be billed, and the router never changes either. Only Grok models, pinned by name: never `auto`, never a third-party model, which Cursor bills at API list price from the first use. A Cursor call refused because the pool is used up stops the task with the reason, as a plan limit does (`redteam`'s second attack is skipped instead, and the run goes on with one attacker; see Relay); it is never resumed and nothing is bought to keep going (see Cursor). Any charge, or any prompt to add credit, is the kill criterion.
- Images are made only by Grok Imagine on the Grok plan. The router asks for at most 4 images per task and never asks for video. No image API, no credits.
- No brokerage access of any kind. This project never touches real money.
- A relay chain has at most 4 stages. Each stage is one agent call, plus at most one contract re-ask for that stage (so one re-ask per stage, not one per chain). When the preset names a checker, the last stage's check is the usual check loop. When the preset's last stage is the check, nothing is spent beyond that stage. When the preset has review stages, the reviews are the checks and nothing is spent beyond the last stage; the owner's pick costs nothing. Nothing more is spent on a chain.
- A redteam task is four stage calls and the usual check loop: the build, two attacks each made on its own (ChatGPT's, then Cursor's), the revision, then the check and one fix round; three stage calls when the second attack is left out or skipped (see Relay). The second attack is one Cursor call from the X Subscription's weekly pool. It costs more than a routed task and less than a split; it is for work worth attacking, not for a quick answer.
- A vote task is three stage calls and nothing else: no checker, no fix round, no re-ask beyond each stage's one contract re-ask. Three calls for one answer; it is for a decision worth three independent opinions, not for a quick answer, and never for a trade: the router never touches money.
- Slot flags change who does a preset's work, never how many calls it makes. A task with its slots filled costs what the preset costs.
- **Run** (brief 31) starts the owner's own program on their click, with its project's keys, as Terminal would. The router itself never trades, never reads a broker account, never gives an agent a broker key, and never reads or acts on what a run does. Run refuses a project whose `.env` holds a name containing an entry of `never_run_env`, this Mac's own list in `config/settings.local.json` (never in a tracked file), and says which entry matched.

## Jev

- Jev sees the task text, the skill descriptions with their `not_for` lines, and the two questions. For a task with files, the task text ends with one line per file giving its name, type and size. Never the file, never its contents. Never a project's handoff. Nothing else is sent to it.
- The model is pinned to a version. The alias that moves on its own is never used.
- The option order is shuffled on every call.
- **Confidence floor: 0.8.** Below it, the router asks the owner which skill, and logs their answer. **On a tagged task** (`--project` or `--chat`) **the floor is 0.4**, because the memory block and the handoff give the agents the context Jev never sees (the owner, 27 Oct, D18). Under 0.4, or `none_of_these`, a tagged task is a **follow-up**, with no question: Claude does it and ChatGPT checks it (ChatGPT does it and Claude checks when Claude isn't available), with its memory block and, on a project, its handoff and file mode, as any routed task; its row reads skill `follow_up`, `skill_source` `router`, with Jev's label and confidence kept, and its doer is told the task may follow from the newest tasks in the memory block. `follow_up` is the router's route: never among Jev's options or the page's chips, and `sr route --skill follow_up` is refused. A label v2 doesn't route, Jev erroring or past its cap, and Jev not set up stay as below. Built by brief 29.1.
- `none_of_these` on an untagged task: the router asks the owner which skill, and logs their answer. If the owner answers none, the task comes back to them.
- If Jev errors or is past its cap, the router asks the owner which skill, and the log says so. There is no second labeler.
- **Jev not set up** (no `JEV_API_KEY`): Jev is never called. A routed task asks for its skill in Terminal, or comes back for its label on the interface, saying "Jev isn't set up: pick the skill" (`jev_status` `not_set_up`); the interface asks for the skill before Send, so the task is one row. Built by brief 24.
- When the router can't ask (no terminal, such as inside Claude Code), the task comes back to the owner with the label shown. A task started from the interface has no terminal: it comes back to the owner the same way, and the interface shows the label and the question with a button for each skill; their answer is sent to the same command a terminal answer goes to (see Interface).
- Every label is logged with its confidence. The "needs two or more skills" answer is logged and not acted on.
- Jev is scored again on the first 30 real tasks it labels, override tasks included, by the owner's judgment. Under 24 right: the router stops using Jev and the owner decides what labels instead. From 24 to 26: Jev stays, but version 2's bar is not met. 27 or more: the bar is met.
- A relay task is never sent to Jev and does not count toward its 30. The preset names every agent. A split's piece whose team is a preset is not a relay task: Jev labels it at plan time (below).
- A resumed task is not sent to Jev again. Its label stands. A fallback is not sent to Jev either.
- A piece of a split is labeled by Jev at plan time, whatever its team. On a route piece the label routes it, as on any routed task; on a piece of another team it routes nothing and is kept in the log beside the planner's team and the team that ran, for a team classifier later. A new text for a piece is labeled again. A piece Jev left under the floor needs the owner's skill only when its team is route; on a project split the floor is 0.4, and a route piece under it, or on `none_of_these`, is a follow-up, as on any tagged task. A piece does not count toward Jev's 30: the owner did not write it, the planner did. The split task itself is not sent to Jev.
- A piece's Jev tokens count toward the monthly cap from the moment it is labeled at plan time, even when the plan is then cancelled. They are counted once, on the split.
- A project task is labeled like any routed task and counts toward Jev's 30 as any task the owner typed does. The `--project` flag changes nothing Jev sees. Neither does `--chat`: Jev never sees a memory block.
- **A 12th skill, `recall`.** A task that asks what the router remembers under its tag (what was done, decided, produced or said, or what comes next) is `recall`: best Claude, second ChatGPT, checked as any skill is; its `not_for` is anything that needs new facts or new work. **Live since 2026-10-20, skill table 3.4** (`368e4d5`). Its text says the answer reports and makes nothing new: any task that produces something, even from an earlier result or "from memory" (writing, rewriting, shortening or redoing a text, planning, code, new facts), is not `recall`. Round 3 of the label test failed on one near-miss (a rewrite "from memory" labeled `recall` at 0.86); the text was sharpened and round 4 passed its bar, written before the run: 60 tasks (the 30 round-2 tasks, round 3's 15, 15 new), Jev 57 of 60 by majority; recall 13 of 13 on every run and `quick_answer` in none of the 39 recall runs; near-misses 16 of 17 with `recall` in none of their 51 runs; the 28 regression tasks still right. A `recall` task with no `--project` and no `--chat` comes back to the owner after Jev's row and before any agent call: `recall needs --project or --chat: nothing to recall from`; an override runs as Overrides says. With a tag, its first call's fresh recall needs the store: when the store can't be reached the task comes back before any agent call with `memory unavailable (the store could not be started): nothing to recall from`, or with `memory: off`, `… (memory is off in settings) …` (see Memory, Down).

## Media

- A task may carry up to 4 files, each 50 MB or less: `png`, `jpg`, `jpeg`, `webp`, `gif`, `pdf`, `mp4`, `mov`. Anything else is refused at intake with the reason, before Jev is called.
- A file goes only to Claude and ChatGPT, as a copy in the agent's workspace for the length of the call, deleted after. Nothing is ever sent to Grok, Muse, Cursor or Jev.
- A task with files whose doer is Grok or Cursor comes back to the owner with the label shown. `@grok` on a task with files is refused.
- A video is never sent to a model. The router pulls up to 12 still frames from it, one every 5 seconds, and sends those. The clip stays on disk.
- A PDF goes to ChatGPT as page images, the first 12 pages, rendered into that PDF's own folder, `media/pages/<task_id>/<stem>/` (its whole file name when two PDFs share a stem), so each PDF on a task reaches ChatGPT as its own pages, in order (brief 24). Claude gets the PDF itself.
- The checker of a media task gets the same files the doer got.
- Copies, frames and images Grok makes live under `media/` in the repo folder, which is in `.gitignore`. An image Grok makes is stored under `media/out/<task>/`.
- The result of `make_media` is the path of each image, with Grok's text. `sr show` prints the paths. Nothing opens on its own.
- A relay task carries no files in version 2. A split task carries no files in version 2.
- On a resume or a fallback, the agent doing the work gets the task's files the way this section delivers them to that agent.
- No agent searches the web on a call that carries a file, unless the owner sent the task with `--web` (see Web search).
- A project task may carry files as any routed task may. The handoff is pasted text in the prompt, never a file in the workspace, so it does not count toward the 4.
- A file dropped on the composer is written into the drop folder (`drop_folder` in settings; `~/Desktop/Router Drop` by default) with an exclusive create, a clash becoming ` (2)` and never an overwrite, Media's types and size checked first, and attached with `--file` as if the owner had typed it. A file dropped on a project's bar goes into the project instead (see Project files, Files in). A `--file` at the drop folder's top level moves to `sent/<task_id>/` once attached, as a y-answered drop does, so the next `sr route` in Terminal never offers it again. The drop folder's y/N question is answered by the file being on the composer when the owner sends; a file the owner removes from the composer stays in the folder and is not attached. The interface never writes a file anywhere but the drop folder. Built by brief 23.

## Web search

- **Claude and ChatGPT may search the web on every call they make**: a routed task's doer, checker, fix round and re-check; every relay stage, whatever its slot or role; a `versus` build and review; a split's plan, integration and pieces; a resume; a fallback. Claude gets search queries and result snippets only. ChatGPT gets the live search its command line gives.
- **Files.** A call that carries a file has no search, for any agent, unless the owner sent the task with `--web`. With `--web`, every call on that task may search, file or not. `--web` is per task, never a setting; it is taken only by `sr route` (the one command that takes files) and refused elsewhere with the reason; the log marks the task. `--web` on a task with no files changes nothing. Why: a search query is a message out of the machine, and on a call with a private file it could carry that file's words; `--web` is the owner saying the file is not private.
- **Never page fetching for Claude.** Claude does not open web pages, only search results. Opening pages is not in version 2.
- The search is decided in code, by whether the call carries a file and whether the task has `--web`, never by the model, the agent's choice, or the task text. Grok searches as it always does; the router never switches Grok's search on or off.
- A search result is data, never instructions. Every prompt that goes out with search on says so, and says to cite where a fact came from.
- Claude is asked for at most 5 searches per call. More is logged on the call row, never refused.
- Each Claude call with search allowed is logged as such. Searches Claude made are kept in the call row when the tool reports them.
- `sr probe` proves it before any search call runs, and after every Claude Code update: one search call on a fixed prompt, with the answer key fixed first, must show that search worked and that no other tool ran, judged from Claude's own tool log, not from what Claude says: a tool call ran unless its result came back with Claude Code's error mark, and a call with no result counts as ran, so a tool Claude asked for and was refused never ran (brief 32's D: Claude Code 2.1.312 asked for Bash, Read and Write, which it didn't have). The check names both lists, and a failure keeps them. Every Claude call with search on is judged the same way (brief 32's D8, built by brief 33.1): a tool Claude asked for and was refused never ran, so it never fails the call; a tool the call doesn't allow that ran (its result came back without the error mark) still does.
- The probe compares `.env` values in memory only and reports found or not found. A value is never printed, logged or stored.
- A probe pass is kept per Claude Code version. A new version turns Claude's search off until the probe passes again. Right before a task's first Claude call that may search, when the installed Claude Code version has no pass, the router runs Claude's missing probes itself (one probe at a time, by a lock), then makes the call. On a chain that starts with Grok that is after Grok's stage, so a task that stops before reaching Claude spends no probe; nobody has to run `sr probe` by hand. A failed probe leaves search off, as before, and the task runs without it. Built by brief 22. Claude Code updates itself (seen live 20 Oct: 2.1.303 to 2.1.304 between two tasks; search stayed off until `sr probe` passed on the new version). `sr probe` also runs Cursor's three canaries when their pass is missing, is from before the third canary, or the agent moved (see Cursor).
- `sr probe` also proves Claude's `--web` file mode: one call with Read and WebSearch on a test file, judged from Claude's own tool log. It passes only if Read touched nothing outside the task's copy folder, no other tool ran (read as the search check reads it), and no `.env` value appears in the answer or any search query (compared in memory, reported only as found or not found). Its pass is kept per Claude Code version, like the search pass. A fail turns off only Claude's `--web` file mode; ChatGPT's half of `--web` still works.
- If the probe fails, Claude's search stays off on every call and Claude works without it. The log says so. ChatGPT's search is not gated by the Claude probe; ChatGPT runs only after its own probe passed on the installed Codex version (see Checking).
- A probe that could not run (a timeout, a process error, no answer) is told apart from one that ran and failed a check, and `probe_state.json` records which, with the version, the reason and the time. One that could not run is tried again by the next task that needs it, at most once an hour per tool and version; meanwhile the task runs as after a failed probe. One that ran and failed stays failed on that version until the tool moves; `sr probe` by hand stays the override in Terminal. A pass clears the record. Built by brief 22.

## Checking

- Every result is checked before the owner sees it, but for Suggest ideas, which is never checked: a deliberate exception, since ideas are judged by the owner, who adds, sends or dismisses each (see Next steps). The checker is the skill's second agent when it is available, then Claude, then ChatGPT: never the doer, never an agent whose call stopped in this task, never Cursor. Grok checks only where the skill table names it as second, and a Grok check that would pass its prompt limit is skipped before sending, said on the card and in the note (`Grok skipped: …`), with no row. With nobody left, the result is delivered `unchecked: no other agent available to check (<why>)`. An override and a relay check as their sections say. Built by brief 24.
- On a relay preset whose last stage is the check, that stage replaces the check loop: its agent edits the deliverable and lists what it could not fix. There is no fix round; the edit is the fix (see Relay). On a project, `collab`'s partner checks with the usual loop instead (see Relay).
- On a relay preset with review stages, each review is a check round without a fix round: the reviewer sees the task and one candidate, returns a verdict and notes, and changes nothing. A reviewed candidate is not the task's result until the owner picks it (see Relay).
- On a relay preset that tallies (`vote`), the tally is the check: three agents answer the same question with nothing but the task, code compares the answer lines, and an answer two or three of them reached on their own is the task's result, marked `checked-by-vote` with the count. There is no checker, no fix round and no fix list. Every voter's answer and reasons are shown with the result, the dissent first. When all three differ, nothing is the result until the owner picks, and a picked answer is delivered marked unchecked: no two agents agreed on it (see Relay).
- A result is never checked in three cases: a Suggest ideas task, the skill is `quick_answer`, or it is an override task in one of the cases the Overrides section lists.
- The checker sees the task and the result. It does not see the builder's reasoning.
- **Must and note** (the owner, 27 Oct, D20, from the design chat's read of every check in the log). The checker lists every problem it finds, once, each tagged `[must]` or `[note]`, and only a must fails the result. A must makes the result wrong or incomplete for the task: a wrong fact, number, date or name; code that doesn't do what the task needs, including a wrong or impossible result for an input it accepts without an error; a part of the task not done; a limit the task sets broken; the result contradicting itself or claiming what it doesn't contain; a change or decision the task didn't ask for that the result makes as settled or applies (a rule, a file or an agreed decision changed without being asked), while a choice that a plan, a recommendation or a proposal puts to the owner to approve is never a must for being new or different from earlier decisions, only a note; an error in a plan (a number, a sum or a schedule that doesn't add up, or a step that can't work); a claim the answer depends on that the result doesn't back, whose fix is always to back it or mark it unverified, never counts, samples or research the task didn't ask for; in file mode, a failing test the result doesn't explain. Everything else is a note, shown on the card under the verdict: wording, tone, hedging, more evidence for a claim not shown wrong, and anything the checker couldn't open itself. "Under N", "at most N" and the like are limits; "an N-word" text is a target that 10% either way meets. Code reads the list: a FIX with no must is a pass with notes; an untagged item is a note after PASS, and after FIX a must unless it is only a source link (a markdown link or a bare URL, or a few with commas between), which is a note (29.1's live check: a check that said PASS, its sources listed untagged, failed twice). On `redteam` an open high attack from either attack list is a must, and an open medium or low one never is.
- **The router's facts.** Every check and re-check prompt says what the router does and the doer can't: the doer had only the task, the blocks in its prompt and, on a project, a copy of the project's files; it can't run a command, commit, land or save to memory; in file mode the owner lands after the check, and the router writes the handoff entry and saves memory. The checker never asks the doer for something it couldn't do or know from what it was given; what the checker couldn't open itself is a note, never a failure. The fix round is told the same. Every check and re-check also gives the task's date ("The task was sent on <date>.", the row's local date) and has the checker check each main claim the answer depends on, as far as its tools allow: a claim it checked and found wrong is a wrong fact, said with what is right and where it was found. Every prompt that returns the deliverable (a routed doer, a build stage, a split's integration, and their fix rounds) says: when the task sets a length, a count or says only, reply with the deliverable alone, and say what is missing or unverified under `## Missing` (`## Unfinished` where a stage's shape has it). Built by brief 29.1.
- One fix round. **The re-check checks the fix:** it gets the first check's list and says of each must `fixed` or `not fixed`; it fails the result only for a must not fixed or a new problem the fix made in what it changed, and anything else it notices is a note; code decides the verdict from those lines (the owner, 27 Oct, D20: half the re-checks' demands in the log were new, so a result could fix every one and still fail). If the result still fails, the router stops and shows the owner both sides: the fixed result and what the checker still wants fixed. The owner may then run a fallback (see Fallback), or land a file-mode change anyway (see Project files).
- **The fix round changes only what the list asks** (brief 30, from 29.1's live check, where two fixes each added a new wrong claim that the re-check then failed): every fix prompt says so, and that everything it changes is checked again.
- A fix round sent to Grok puts the fix list before Grok's own earlier result in the prompt, so a cut in delivery drops the old result's tail, never the fix list.
- If a check round or a fix round stops, the router first hands it on once (see Takeover). Only when nothing can take it does it tell the owner which round failed and why, and give them the furthest result the loop produced. A result whose check did not finish is marked unchecked.
- After a fix, the owner gets the fixed result. The original is kept and shown only when the owner asks. In the interface, "asks" is a button on the task that reads the first build's round file (see Round outputs); nothing is shown before the owner presses it.
- No agent checks its own work. On `collab`, ChatGPT amends the plan and later edits Claude's build: it checks Claude's build against the task, never against the plan, and never its own text. On `versus`, each builder reviews the other's candidate and never its own. On `redteam`, an attacker may be the checker: it attacked the build and checks the revision, and neither is its own text; Cursor, the second attacker by default, never checks. On `vote`, no agent checks anything: the agreement of agents that never saw each other's answer is the check. After a takeover, the checker follows the order above and is never an agent that just stopped (see Takeover); a fix round taken over by the task's own checker is delivered unchecked, since nobody is left to re-check it. On a manual resume, when the substitute would be the checker of its own work, the other builder checks instead (see Resume). On a fallback, the original doer checks the checker's redo (see Fallback). On a split, each piece is checked as the routed task it is, and the integrated result is checked by ChatGPT against the original task, or delivered unchecked when ChatGPT isn't available. Slot flags cannot make an agent check its own work: intake refuses them (see Relay).
- A result that could not do the task never passes. **When a result says it couldn't do the task because the doer lacked what it needed** (in neither the task, its blocks, its memory nor the project's files, and not to be found by a search it could run), the checker answers `BLOCKED` and names what it needed: the task ends blocked (status `failed`, `check_state` and `outcome` `blocked`), with no fix round, no fallback, no resume and nothing stored, and the card says what to add; on a project its handoff line reads `blocked: <what it needed>`. Otherwise the checker asks for the fix. The owner, 27 Oct (D20). A result that did the work and found fewer things than asked is judged on its evidence. A result that did the task is never blocked: what the checker couldn't check itself is a note.
- A checker that cannot reach what the result is about gives a sanity check only, and says so: the web for `web_research`, `x_social_pulse` and `meta_social_trends`, and a file it cannot view. For every other skill, reading the result is the full check. Claude and ChatGPT reach the web on every call without a file, and on a `--web` task (see Web search); a checker on a file call without `--web` does not.
- **Meta research done without a live feed** (a stand-in or takeover on `meta_social_trends`): after the no-result rule, the checker gets one more line: "The doer had no live feed of X or Meta posts, only web search. An answer that names its sources and says plainly what the open web could not show is an answer: judge it on its evidence, and fail invented posts, unsourced claims, or a result that hides the gap." The owner, 21 Oct, after the live check failed an honest stand-in answer twice. The same check still failed X research done by web search, so `x_social_pulse` has no stand-in (see Availability). Built by brief 24.
- A relay task has no skill, so the line above is read by what the result is about, not by a skill. A relay checker may use web search. A relay checker that cannot reach what the result is about gives a sanity check only, and says so. A split's integration check is read the same way.
- A relay checker judges a result on the evidence it has. When the result openly says what its research did not cover, the checker does not fail it for that gap and does not ask for new research; it fails a result only for what is wrong, unsupported, or hidden. The checker prompt says so. A reviewer on `versus` judges the same way. So does the check on a split's integration.
- On `research-build` the check and the re-check are told the result was built from a research note they don't get: a claim the result attributes to that note counts as backed (judged for whether the result uses it consistently, and checked where a search can), and a claim that names no source is judged as any claim (brief 29.1, Proof 2's round 2).
- A reviewer on `versus` gets a candidate's `## Missing` section as the builder's own note, labeled apart from the deliverable. It judges the deliverable against the task, reads the note as what the builder says it could not do, and never fails the deliverable's format or length because of the note.
- **On `redteam`, the checker also gets the attack lists** (two since brief 32, each labeled with its attacker; one when the second attack was left out or skipped), as data, labeled apart from the result. It fails the revision for any high-severity attack in either list that is neither fixed nor answered: answered means the revision says, in its `## Answered` section, why that attack does not apply, with a reason the checker finds sound. It does not fail the revision for a low or medium attack left open, and it does not add attacks of its own: the check is still the check, judged on the evidence, and the attack list is one more thing to check against. The fix list names the attack by its label (`A2`, `B1`; see Relay), or by its number on a task from before brief 32. The `## Answered` section is the reviser's note, not part of the deliverable: the checker never counts it toward the task's length or format.
- On a project task, the checker also gets the handoff and judges the result's handoff section for what is false: a `### Produced` line that names something the result doesn't contain or a file the change doesn't touch, or claims something it didn't do, is a must; wording, a heading quoted inexactly, or a line that could say more is a note (the owner, 27 Oct, D20); the fix round carries the handoff as the doer's "stage before". A missing or malformed section is a contract miss, not a verdict: it gets the one re-ask before any check (see Project context). In file mode the checker also gets the change and the test results as data (see Project files).
- On a task with a memory block, the checker gets the same block as the doer, labeled as data, and one more line: a result that leans on a recalled memory that is off the point, or that the task or the result itself contradicts, fails, and the fix list names the memory by its task number. The checker does not fail a result for ignoring a memory it did not need. No extra call.
- **Built from an earlier result** (brief 33). On a task sent with `--from`, a check, re-check, review or attack gets the earlier result's block, as the doer does, and one line: a claim the result takes from it is backed by it, still checked as any main claim where the checker can, and an earlier result found wrong is said so. No extra call (see Next steps).
- **A plan and its steps** (brief 33.1). A plan's check and re-check get both attack lists, the copy's file list, the project's last Test's outcome and the plan's check line; a step's check and re-check get the finish-line line. Both are written out in The plan.
- **Router notes** (brief 30). A check, re-check, review or attack carries the judge's own router notes and one line: not following the person's notes is never on its own a must, a fail or a high attack; at most a note. The notes the doer had are not the judge's to judge.
- **The word count is code's.** Before every check and re-check, on every preset and on a routed task, the router counts the words of the deliverable (the result before any note section: `## Missing`, `## Answered`, `## Unfinished`, `## Next`, `## Handoff`) and tells the checker the count on one line, placed before the task and result blocks so a cut in Grok's delivery never drops it, with the task's own words about length if the task has any, which the router never parses into a number. The checker judges length against the task from the count, not from its own estimate; a result over a limit the task states fails. The fix round gets the same count line. No extra call, nothing a model counts.
- A Grok call that Grok Bot refuses is a failed round. Grok is never asked again; the call is taken over once as Takeover says.
- **ChatGPT's safety check runs itself.** A Codex probe pass is kept per Codex version in `probe_state.json` (`codex_sandbox`), as Cursor's is. Before ChatGPT's first call on a Codex version with no pass, the router runs the probe once (one ChatGPT call, one probe at a time by a lock) and goes on only after a pass. One that ran and failed turns ChatGPT off on that version, said in plain words: its work goes to the other agents (see Availability and Takeover). One that could not run is tried again after an hour. `sr probe` stays the manual override and records the pass. Built by brief 24.

## Availability

- **Available** means: the agent's live flag is on; it is set up and answering (Claude signed in with the plan; ChatGPT with a pinned model and `codex` signed in with ChatGPT; Grok Bot with `GROK_WEBHOOK_URL` and `GROK_WEBHOOK_KEY` in `.env`, `grok_inbox_repo` set and that repo answering a read; Cursor with a pinned Grok model and `agent` signed in); and no safety check failed on its installed version. It is checked when a task comes in, only for the agents the task needs, side by side, by checks that are never a model call (see Money); the reason is said in plain words.
- **Claude is required.** `route`, `relay`, `split`, `plan` and `auto` refuse every task while Claude isn't available, before any row, with the reason. Every other agent is optional.
- **A check that doesn't answer** (a timeout, or it couldn't start) is tried once more. If Claude's still doesn't answer, the task goes ahead with a warning ("Claude's sign-in check didn't answer; trying anyway"): the call itself decides, and a real failure is taken over. Any other agent whose check still doesn't answer is unavailable for that task. The owner, 21 Oct, after the live check saw `claude auth status` miss its 15 seconds once.
- **Who does a routed task:** the best agent, then the skill's `interim` (when set; null on every skill today), then its second, then Claude, skipping any that isn't available. The card says so ("ChatGPT did this · Grok Bot isn't set up"); a stand-in is not a takeover. **`make_media` and `x_social_pulse` are Grok Bot's alone**, since nothing else makes images with Grok Imagine or sees X posts: without Grok Bot the task comes back as `unavailable` ("<skill> needs Grok Bot: <why>") before any agent call, and their Grok calls are never taken over (see Takeover). `x_social_pulse` joined after the live check, where web search couldn't see X posts and both stand-in runs failed their check (the owner, 21 Oct). A task with files still comes back when its doer would be Grok or Cursor (see Media).
- **Meta research by another agent:** a stand-in or takeover on `meta_social_trends` gets one prompt line: "You have no live feed of X or Meta posts, only web search. Name where each claim came from, and say plainly when the open web could not show what people are saying now." The card says "done without Meta".
- **Presets:** a slot whose default agent isn't available is filled by the other of Claude and ChatGPT (a Grok slot: ChatGPT, then Claude) when every slot rule still holds; otherwise the task is refused at intake, naming the slot and why no other agent can take it. A slot set by flag is never refilled. `redteam`'s second attack is the exception to the refill: when its default agent isn't available it is left out, the task runs with one attacker, and the card says why (see Relay). Without Grok Bot, research-build researches with ChatGPT and vote is refused; without ChatGPT, research-build, collab, versus, redteam and vote are refused.

## Overrides

- A task starting with `@claude`, `@grok` or `@chatgpt` is done by that agent, whatever its label.
- Jev still labels the task, only to pick the checker. The checker is the skill's second agent. If the named agent is the second agent, the skill's best agent checks. A `quick_answer` task is never checked (see Checking).
- The task still runs, and its result is not checked, when Jev's answer is below the floor or `none_of_these`, when Jev errors or is past its cap, or when the label is a skill not routed in v2. The router does not stop to ask the owner, because the owner already chose the agent.
- For an override task, the line above replaces the Jev section's rules on those cases.
- The log marks the task `override`, with Jev's label and confidence.
- Each new agent gets its own override when it goes live. `@cursor` came with Cursor's live flag (20 Oct); with the flag off it is refused at intake with the reason, as any unknown prefix is (see Cursor). An override of an agent that isn't available is refused at intake with the reason (see Availability).
- An override prefix on a relay task or a split task is refused at intake. An override prefix with `--project` is refused at intake: an override may run unchecked, and a project task's handoff section is never written unchecked. An override with `--chat` is allowed: an override's unchecked result is never stored as a memory, so the tag costs it nothing (see Memory).
- An override task is never taken over, never resumed on a plan limit and never falls back. The owner chose the agent; the owner runs the task again. A process-ended stop is resumed by the same agent (see Resume).
- In the interface, `@claude`, `@grok` or `@chatgpt` typed at the start of the box is the same override: the text is sent to `sr route` as typed. The interface adds no prefix of its own.

## Relay

- `sr relay <preset> "<task>"` runs a chain: a fixed list of stages, one agent per stage. The presets live in `config/presets.json`. A preset whose default names an agent that isn't available is filled at intake or refused there (see Availability); one that names a checker that is its last stage's agent, or has more than 4 stages, is refused at intake with the reason; one that names an agent `agents.json` doesn't have, or the router can't send to, is refused at load.
- **What a stage gets.** By default, the task and the result of the stage before it, never more. A preset may instead name a stage's input: the task alone, or the result of one named earlier stage. A stage never gets the result of a later stage, or of more than one stage. There are two exceptions: a split's integration call, which gets every piece's result (see Split), and a revise stage, which gets its own agent's earlier result and the one or two attack lists it answers (below). On a project task, every stage also gets the handoff, as data (see Project context).
- **Revise stages.** A preset may mark a stage as a revision of one named earlier stage by the same agent, against one other named earlier stage's result, or, since brief 32, against two attack stages of the same build. It gets the task, its own earlier result, and that other result (or both attack lists, each labeled), as data, the way a fix round gives a doer the task, its own result and the fix list. The revised stage and the revise stage must have the same agent, and both named stages must be earlier. A preset that breaks this is refused at intake with the reason. Only one revise stage per preset.
- **Attack stages.** An attack stage is a stage whose job is to find what is wrong, weak or missing in an earlier stage's result and nothing else: it never rewrites, fixes or completes the result, and its output is a list, never a deliverable. An attack is data to the stage that revises against it; it is not a verdict, and the task's result is still checked as any result is. The attack stage's agent must not be the agent of the stage it attacks. **Two attackers** (brief 32, D25): two attack stages may attack the same build, each given the build alone and never the other's list, by two different agents, neither of them the builder. Code labels their items by stage, the first list's `A1`, `A2`, … and the second's `B1`, `B2`, …, and every later prompt, the fix list, `## Answered`, the card and the JSON name an attack by its label; a list is never rewritten. The second may be marked optional: when its agent isn't available at intake it is left out, and when its call fails or its contract is still missing after the re-ask it is skipped. Either way the chain goes on with the lists it has, nothing takes the stage over, a plan limit never makes it resumable, and the card says why; a process-ended stop during it is resumed by hand by the same agent, as any is.
- **Tally presets.** A preset may name the tally as what picks its result. Then every stage is a vote stage: it gets the task alone, never another stage's result, and returns one answer line and its reasons. A tally preset has an odd number of stages, at least three, each with a different agent; it names no checker, marks no check stage, and has no review, attack or revise stage. Code normalises the answer lines (case, spacing, trailing punctuation, one pair of surrounding quotes, one pair of emphasis marks such as `**`, `_` or backticks, and a leading "the"; a number in digits and the same number in words are still two answers) and counts them: an answer with more than half the votes is the task's result, byte for byte the result of the first stage that gave it, and the task's check reads `checked-by-vote <for>/<against>`. No majority: the task waits for the owner, as a review preset does, and `sr pick <n> a|b|c|none` picks. A picked answer is delivered marked unchecked; `none` ends the task as failed with every answer kept. A tie is never broken by a model, by a confidence number, or by the router. A preset that breaks any of this is refused at intake with the reason.
- A preset may instead mark its last stage as the check (`is_check`). Then it names no checker, and the check stage's agent must not be the agent of the stage before it. A preset that both names a checker and marks a check stage, or does neither and has no review stages and no tally, or marks a stage other than the last, is refused at intake with the reason.
- **Review stages.** A preset may mark a stage as a review of one named earlier stage. A review stage's agent must not be the agent of the stage it reviews, and the stage it reviews must not itself be a review. A preset with review stages names no checker and marks no check stage; every stage that is not a review must be reviewed exactly once; and the preset names the owner as the one who picks. A preset that breaks any of this is refused at intake with the reason.
- **A candidate is its builder's deliverable.** A builder may list what it could not do in a `## Missing` section after the deliverable, and only when something is missing. The owner sees that section under the candidate. It is never part of the picked result, and it does not count against a length or format the task asks for.
- Jev is not called. The preset names each stage's agent and the checker, or marks its last stage as the check, or marks its reviews. The log marks the task `relay` with the preset's name.
- A stage's result is data to the next stage, never instructions. The prompt says so. A reviewer gets the task and the one candidate it reviews, never the other candidate.
- Every stage but the last has a contract: what its result must contain, checked in code, never by a model. The exception is a stage that a review stage reviews: its review is its check, and it needs no contract. A result that misses it gets one re-ask naming what is missing. Still missing: the chain stops. A check stage has a contract too, because code reads its `## Unresolved` section to set the verdict. A review stage has a contract too, because code reads its `## Verdict` to set the candidate's verdict: `pass` or `fail`, with `## Notes` under it. An attack stage has a contract: a numbered `## Attacks` list of at least three, each with a severity, and one `## Strongest` line. A vote stage has a contract: `## Answer`, one non-empty line, and `## Why`, at least one line; a `## Confidence` line (0 to 100) is asked for, shown when given, never required and never counted; it is read from the stored answer when shown and never stored on its own. An empty or unreadable verdict is a missing contract, not a verdict, and gets the one re-ask. On a project task, the last stage before the checker has the handoff contract too (see Project context).
- When the preset names a checker, the last stage's result is the task's result and is checked as any result is (see Checking). The checker sees the task and that result, not the earlier stages, except on `redteam`, where it also gets the attack lists. The fix list goes back to the last stage's agent with the task, the result of the stage before, and its own result. On `redteam` the fix round's result keeps its `## Answered` section and is read with the revise stage's contract: one re-ask, and still missing, the fix round fails and the revision is delivered with the fix list.
- When the last stage is the check, it gets the task and the result of the stage before, as any stage does, and returns the full deliverable after its edits, the list of edits it made, and what it could not fix. `## Unresolved` reading `none` is a pass, and the task's result is that stage's deliverable. Anything else written there is a failed check: there is no fix round, the router stops, and the owner gets that stage's deliverable and the unresolved list. An empty `## Unresolved` is a missing contract, not a verdict: it gets the one re-ask. The result of the stage before is the original, kept and shown only when the owner asks. The log marks the task's check `checked-by-stage`. If the check stage's contract is still missing after the re-ask, the chain stops as any stage does, and the result of the stage before is marked unchecked.
- **When the preset has review stages**, the chain ends with every candidate reviewed and no result chosen. The router shows the owner each candidate with its reviewer's verdict and notes, and waits. `sr pick <n> a|b|none` records their pick: the picked candidate becomes the task's result, with its review as the task's check; `none` ends the task as failed with both candidates kept. Their pick is logged like any answer of theirs. One pick per task; a second is refused. The unpicked candidate is kept and shown only when the owner asks. Nothing is the task's result before the owner picks. In the interface, a pick is a button that first asks them to confirm and then runs the same command (see Interface).
- A stage that stops is first taken over (see Takeover). A stage nothing can take, a contract still missing after the re-ask, or a cancel stops the chain. The owner gets every stage's result so far, and the log says which stage failed and why. A stopped chain is stored with status `failed`, the failing stage and the reason, not a status of its own. Nothing is retried beyond the one contract re-ask. A chain stopped by a plan limit the takeover could not take may be resumed once by hand (see Resume), except a chain with review stages or a tally, which is never resumed or taken over.
- Stage results are not shown to the owner unless the chain stops, the chain is waiting for their pick, or the owner asks (`sr show <n> --stages`). The result of a stage the owner never sees is not a result for the Checking section; only the last stage's is, or on a review preset the candidate the owner picks. On `redteam`, the attack lists are shown with the result, under it, each under its attacker's name, so the owner sees what the revision had to survive; when the second attack was left out or skipped, one line says why. On `vote`, every voter's answer, reasons and confidence are shown with the result, the dissent first; there is no stage the owner does not see.
- Each stage is a call row in the log with its stage number and role. The task row carries the mode, the preset, and the agent in each slot.
- No files on a relay task. No override prefix.
- Presets in version 2: `research-build` (stage 1 Grok research, contract a note with `## Findings` (at least 3 lines), `## Sources` (at least 3 lines with links) and `## Gaps`; stage 2 Claude build, with web search (see Web search); checker ChatGPT, with web search); `collab` (Claude plans, ChatGPT amends the plan, Claude builds from it, ChatGPT edits the build as the check; on a project ChatGPT checks the build with the usual loop instead); `versus` (Claude and ChatGPT each build from the task alone, neither seeing the other's work; ChatGPT reviews Claude's candidate and Claude reviews ChatGPT's; the owner picks); `redteam` (stage 1 Claude builds from the task alone; stage 2 ChatGPT attacks the build, returning `## Attacks`, each numbered with a severity of high, medium or low, and `## Strongest`; stage 3 Cursor attacks the same build on its own, never seeing stage 2's list, in the same shape, and is optional (see Attack stages; brief 32); stage 4 Claude revises its own build against both lists, returning the revised deliverable and an `## Answered` section naming by label any attack it rejects and why; checker ChatGPT, with both lists, failing any high attack in either that is neither fixed nor answered); `vote` (Claude, ChatGPT and Grok each answer the task alone, none seeing another's answer; code tallies the `## Answer` lines; the answer most of them reached is the result; three different answers go to the owner's pick). Any other preset is added by its own brief, one at a time, and named here when it lands.
- **Slots.** Each preset names its slots, the parts an agent fills, and each slot's default is the agent the preset line above names:
  - `research-build`: `research` (stage 1), `build` (stage 2), `check` (the checker).
  - `collab`: `lead` (stage 1, the plan, and stage 3, the build) and `partner` (stage 2, the amended plan, and stage 4, the edit as the check).
  - `versus`: `a` (builds candidate A at stage 1 and reviews candidate B at stage 4) and `b` (builds candidate B at stage 2 and reviews candidate A at stage 3).
  - `redteam`: `build` (stage 1, the build, and stage 4, the revision), `attack` (stage 2), `attack2` (stage 3, the second attack; brief 32), `check` (the checker). `attack` and `check` may be the same agent; they are, by default. A task from before brief 32 has no `attack2` and ran three stages, the revision at stage 3; it is read as it ran.
  - `vote`: `a` (stage 1), `b` (stage 2), `c` (stage 3). Defaults Claude, ChatGPT, Grok. With three live agents a slot flag can only change the order, and the order matters once: a Grok stage waits for `sr check`, so Grok goes last by default.
- `sr relay <preset> "<task>" --<slot> <agent>` puts that agent in that slot for this task only. A slot left out keeps its default. The preset itself never changes.
- **Intake on slots.** With its slots filled, the task must pass every rule a preset must pass (an agent that is live; a checker that is not the last stage's agent; a check stage's agent that is not the agent of the stage before; a reviewer that does not review its own candidate; an attacker that does not attack its own build), and also: `build` and `check` are different agents; `lead` and `partner` are different agents; `a` and `b` are different agents; on `redteam`, `build`, `attack` and `attack2` are three different agents; on `vote`, `a`, `b` and `c` are three different agents. A slot the preset does not have, an agent name that does not exist, or a slot named twice is refused. Every refusal comes at intake, with the reason, before any call is made or any row is written. Slot flags on `sr route`, on a split task or on `sr plan` are refused; a split's piece takes its slots from the split's plan (see Split), and a plan task runs `redteam` as it is filled now (see The plan).
- Any live agent may fill any slot, Grok included, with one exception: Cursor may fill `versus` `a` or `b` (it builds a candidate and reviews the other, and the owner picks, so its review is advice to them, never a verdict the router acts on), and, after rule 12, the `build` slot of `research-build` and `redteam` and the `lead` of `collab`; and, since brief 32 (D25), `redteam`'s `attack` or `attack2` (`attack2` is its default), on a task with `--project` too, where it gets the build or the change as text like any attacker; never a `check`, `partner` or vote slot in version 2, and never another slot on a task with `--project`, which is refused at intake with the reason (see Cursor). A slot Cursor fills runs as every Cursor call does. A slot Grok fills runs as every Grok call does: sent to the webhook, collected by `sr check`, taken over when it stops or is overdue (see Takeover), never resumed by hand, never the fallback doer.
- The task row records the agent in each slot. Every later step reads who does what from the task's slots and its call rows, never from the preset's defaults: the chain, the check loop, a contract re-ask, a resume, a fallback, `sr show`, `sr log`.
- **Grok's prompt limit.** Grok Bot's delivery cuts a prompt past a limit (about 3,900 characters, seen on #55 and #59). Brief 15 measures it once; the owner writes the number in `config/settings.json`. A Grok call that hands Grok an earlier result to judge or build on (a check, a re-check, a review, an attack, a revision, or a relay stage that gets an earlier stage's result) is never sent past the limit: a check or re-check is skipped before sending and the next checker checks (see Checking); a stage fails with `too long for Grok (<n> characters)` and is taken over (see Takeover). A Grok fix round and a Grok contract re-ask are exempt: a fix round's fix list comes first (see Checking), and a re-ask carries Grok's own result, not an earlier stage's. A Grok vote stage carries no earlier result, so its send is never cut, but its whole prompt is measured at intake: a vote whose Grok prompt would pass the limit is refused before any call or row, with both lengths printed, and the owner runs it with another agent in that slot. A project's handoff on a Grok call is trimmed to fit, never failed (see Project context). A memory block on a Grok call is trimmed to fit before the handoff is touched, never failed (see Memory).
- `--project` on a relay task: allowed on every preset (brief 29.1; the owner's D18 and D21, 27 Oct). On `research-build` and `redteam` the last stage before the checker is one agent's build and carries the handoff section. On `collab` the lead's build carries it and the partner checks it with the usual loop in place of its edit stage, since only Claude changes files and one agent owns the handoff; in file mode the lead is Claude, and its plan reads the copy. On `versus` each candidate returns a handoff section and the picked one's is the entry; in file mode the two candidates build in two copies and the slots must be Claude and ChatGPT (see Project files); the owner's pick waits to land. On `vote` every voter gets the handoff and the memory block, no copy is made, and the router writes the entry for the answer.

## Split

- `sr split "<task>"` runs a task in pieces. Claude plans the pieces and gives each a team; the owner approves the plan, after changing any piece's text or team if the owner likes; each piece runs as its own task with its team, one at a time; Claude integrates the piece results into one result; ChatGPT checks it against the original task with the usual loop (without ChatGPT, the integration is delivered unchecked, said from the start). A split may run on a project (see On a project, below). On the page, Split comes just before Plan, the last team (see Interface).
- **The plan.** Claude returns 2 to 4 pieces, each a task that stands alone and needs no other piece's result, with a `team:` line and a one-line `why:` under it, and one line on how the results join. The contract is checked in code: the count; that every piece has text, under 400 characters and not starting with `@` or `/`; that every piece has one `team:` naming a team on the menu and one `why:` under 200 characters; that the joining line is present. A plan that misses it gets the one re-ask, with the menu again; still missing, the split stops.
- **The menu.** Every planner call carries the teams a piece may take, built by the router from `config/presets.json` and what is available now, and typed nowhere else: each team's name, its description, its chain as it would be filled now, and its calls. Route's line is the router's: Jev labels the task; the skill table picks who does it and who checks it. Without a project a piece may take route, `research-build`, `collab`, `redteam`, `versus` or `vote`; on a project, route, `research-build`, `redteam`, `collab` or `vote`, never `versus` (a split has one copy, and versus needs two; brief 29.1). A team that can't run now is not on the menu. When the task names a team for a part, the planner gives that part that team if the menu has it, and says so in its why if not. The owner's judgment on which team fits what is the `## Planner` part of their router notes, which the plan call and its re-ask carry (see Router notes); it is never in code.
- **What the planner may not split.** No two pieces ask for the same search or the same work. Work that needs another part's result stays in one piece with that part: a function and its tests are one piece. A task that is one chain, where each part needs the one before, gets no plan: the planner returns `## No split` with one line saying why, the split stops with that line, and the owner routes the task instead. `## No split` is an answer, not a contract miss, and gets no re-ask. The planner prompt says all of this.
- **The approval.** The router shows the owner each piece: its text, its team, the planner's why, where it goes (a route piece: the agents the skill table picks from Jev's label; another team: its chain as filled now), Jev's label, and whether it will need their pick; then the joining line and the router's count of the agent calls from there, with the most the fix rounds could add (Jev's labels counted apart). Nothing runs until the owner says yes. Before that the owner may change a piece's text, its team or, on a piece of a preset team, its slots, in Terminal (`e`) or on the page (`sr split --edit <n> --piece <k> [--team <team>] [--slot <slot>=<agent>] [-- <text>]`): a new text must meet the piece rules and is labeled again by Jev; a new team must be on the menu and clears the piece's slots; a slot must pass the check `sr relay <team>` gives a slot flag and the project's rules (no Cursor on a project piece; on a file-mode project the build slots stay Claude's). The planner never sets slots. What the owner approves is what runs, and the log keeps the planner's text and team beside theirs. Without a terminal, the split stops at the plan and `sr split --go <n> --answer y|n` answers it, with `--skill <k>=<key>` for a route piece Jev left under the floor. At the approval each piece must pass the intake its own command would apply (`sr route`, or `sr relay <team>`, with the split's project), the open-task rule aside, since the split is the project's open task: one that fails refuses the approval, naming the piece and the reason, and no piece is made. In the interface the plan waits in Needs you, with Approve and Reject each asking once.
- A piece task is created only from an approved plan. This is the one case in which the router creates a task the owner did not type, and the approval is what allows it. The log marks a piece `piece` with its parent task and its team; the parent is marked `split`.
- **How pieces run.** One after another, in plan order. A route piece runs as a routed task, with its own label, doer, checker and fix round. A piece of another team runs that preset's stages and checks, with its slots (the defaults the router fills now, or the ones the owner set on the plan), as `sr relay <team>` would. Each follows the usual rules on a Grok return, a plan limit, a takeover, a resume or a fallback, and the owner's commands work on it by its own number. At most one piece of a split has a Grok call out at a time: a piece's Grok call is not sent while another piece's is out, and pieces for other agents run meanwhile. Whatever ends a piece (its own run, `sr check`, a resume, a pick, a skip, a fallback, a cancel) goes on with its split in the same command, after the same refusals and Claude's gate as `sr split --go`. `sr check` on the split task reports which pieces are done.
- **When a piece is done.** A piece counts as done when it is delivered: passed, or delivered unchecked; a `versus` piece, or a tied `vote` piece, when the owner has picked an answer, whatever its review said. While it waits for their pick it blocks nothing: the next pieces run and only the integration waits. A piece that failed its check twice, stopped, came back to the owner, was cancelled, or was picked `none` blocks the split until the owner resolves it with the piece's own commands or tells the split to go on without it (`sr split --skip <piece>`), in which case the integration prompt says the piece is missing. `--skip` cannot skip the last piece that is not skipped: at least one piece must be delivered for the split to join anything.
- `sr cancel <n>` ends a split that is waiting on the owner, at its plan or on its pieces. It cancels the split only: its pieces are untouched and its plan is kept. A project split is the exception (below).
- **The integration.** When every piece is done, Claude gets the original task, the joining line, and each piece's result in plan order, as data, and returns one result. ChatGPT checks it against the original task with the usual loop; the fix round carries the piece results as the integration's "stage before". A fallback on a split task has ChatGPT integrate from the same pieces and Claude check, except on a project split in file mode, which has no fallback.
- **On a project.** `sr split --project <name>` is taken as `sr route --project` is: a name in the registry, a readable handoff, no open task on the project. The split is the project's one open task from intake until it ends, lands or is discarded, at its plan and on its pieces too; its pieces carry the project tag and are part of it. In file mode (see Project files) the router makes one copy at intake, owned by the split, and the plan call reads it with the handoff. The pieces build in it one at a time: a piece starts only when every piece before it is done or skipped; the router snapshots the copy as the piece starts; the piece's checker judges its own part of the change, from that snapshot, and the project's tests run once, after the pieces are joined. A blocked piece holds the pieces after it; Skip first puts the copy back to that piece's starting snapshot, and is refused while the piece is running; a piece's cancel leaves the copy. A piece never waits to land: only the split lands, and `sr land`, `sr undo` and `sr discard` refuse a piece. The integration is a Claude build call in the copy: it gets each piece's result and the files each changed, may change files to make the pieces fit, and returns the split's one handoff section; the tests run, and ChatGPT checks the whole change. Delivered with a change, the split waits to land: Land puts the whole change in the folder as one commit with the split's one handoff entry, and Undo takes it all back. Pieces get the handoff and the project's memory like any task of the project; they return no handoff section, write no entry and store no memory, and a later call's memory block never takes a piece as its newest task: the split writes one entry and stores one memory. A piece of a project split has no fallback. `sr cancel` on a project split also cancels its open pieces and removes the copy. Without file mode, a project split runs handoff-only, its pieces still one at a time in order, and its card says why.
- At most 4 pieces. A piece carries no file and takes no override prefix, and is never itself a split; its slots come only from the plan. A split task carries no file and takes no override prefix, `--web` or `--chat`: sent from a chat on the page, it goes untagged.
- The split's result is the integrated result. Piece results are kept and shown by `sr show <n> --pieces`, and each piece is shown by its own number.
- Built by brief 11 (rules 2.18); on the page, on a project and with a team per piece by brief 29 (rules 2.41).

## Takeover

- **When a call stops, the router hands it to the next agent at once, by itself, once per task.** Three kinds of stop: a failed call (a send that fails: a webhook error, a sign-out, "model at capacity", any agent error; a local call that times out at its 600 seconds; a relay stage too long for Grok); a plan limit on Claude or ChatGPT; and no answer by overdue (a Grok call still out at 2 × `grok_timeout_minutes`, 10 minutes today).
- **Who takes over.** On a routed task or a piece, a doer's call (do, fix) goes to second place, then Claude, then ChatGPT, and a check round to the next checker (see Checking). On a relay task, a stage or a check round goes as Resume says (the other of Claude and ChatGPT, every slot rule kept); a Grok stage goes to ChatGPT, then Claude, whichever keeps every slot rule. A split's plan and integration calls go as Resume says. Every pick skips the agent that stopped, any agent already stopped in this task, any agent that isn't available, Cursor, Grok on a task with files, and Grok when the prompt would pass its limit. A Claude build, revise or fix call on a file-mode task is never taken over: no other agent can change files (see Project files). Nor is a plan task's Claude call, which reads the project's files (see The plan).
- **What it gets:** what the stopped agent was sent (its files, the handoff and the saved memory block), never the stopped agent's partial output. Its row is `<stopped call>-takeover` and names the stopped call.
- **Who checks after it:** the order in Checking; on a relay task, the preset's checker, else the other of Claude and ChatGPT when that agent isn't the doer and hasn't stopped; with nobody left, the result is delivered unchecked with the reason. Never an agent that just stopped.
- **Not taken over:** a cancel; a contract still missing after its re-ask; an error in the router's own code (`internal_error`); a process that ended (resumed by hand by the same agent, see Resume); a check failed twice (see Fallback); an override; a Cursor call; `redteam`'s second attack (skipped instead; see Relay); a `versus` or `vote` task; a fallback's redo, or any call after a fallback; Grok's call on a skill that is Grok Bot's alone (`make_media`, `x_social_pulse`: at 2N it gets only the overdue note, its answer is the task's answer, checked as usual, when it comes within every Grok call's 30 minutes, and a failed send fails the task with its reason); a second stop on one task. When the takeover's own call stops, the task ends with both reasons.
- **A late Grok answer is logged, never used.** A Grok call taken over at overdue stays stopped (`overdue`). When its answer arrives within 30 minutes of the send, `sr check` stores it on that row, marked late, with its round file, closes the issue, and changes nothing else: never the result, never checked, never in memory. Without the test hook below, a command never takes over the Grok call it just sent: the overdue takeover happens in the next `sr check` (the interface runs one a minute while it may come), or in route's own Terminal wait.
- **The card and Terminal say who took over and why**, in one line ("ChatGPT took over the first call · Claude hit its plan limit"). The log keeps the stopped row and the takeover row.
- **Budgets:** one takeover per task, apart from the one manual resume and the one fallback; a process-ended stop stays resumable after a takeover; no takeover after a fallback.
- **Test hooks**, on a scratch log only (refused on the real log): `SR_INJECT_PLAN_LIMIT=<agent>` answers that agent's call as a plan limit, the way its stream reports one (a Claude search call as an error result event); `SR_INJECT_OVERDUE=grok` logs a command's Grok sends 2 × `grok_timeout_minutes` early, and the sending command reads its own call overdue and takes it over at once. Without the hook, route's own wait takes over at 2N. `SR_INJECT_FAIL=cursor` fails Cursor's next call at its process boundary (exit 1, one line on stderr), with no model call, so a live check sees `redteam`'s second attack skipped (brief 32). `SR_INJECT_QUESTIONS=plan` answers a new plan's stage 1 with three fixed questions in place of the model call (brief 33.4).
- Built by brief 24 (the owner's decisions of 21 Oct).

## Resume

- `sr resume <n>` continues task `n` by hand, for what the router does not take over itself: a process-ended stop, and a plan-limit stop the takeover could not take that a resume still can. On a plan limit the other of Claude and ChatGPT does the stopped call, and the task goes on from there as it would have: the rest of the chain, then the check.
- A task can also be resumed when its check round, fix round or re-check round stopped on a plan limit, even though the task then ended done and unchecked rather than failed.
- Only a plan-limit stop and a process-ended stop are resumable by hand. An error, a Grok refusal or an overdue Grok call is taken over by the router instead, where Takeover allows; a contract still missing and a cancel are neither. Nothing is retried by the agent that stopped, except on a file-mode task: any stop (a plan limit, an error, a timeout, a process ended) of a Claude build, revise or fix call, or of a plan task's Claude call (see The plan), is resumable by hand once per task while its copy is there; the router puts the copy back to its snapshot from before that call and Claude makes the call again (see Project files).
- **A process-ended stop** is a task whose `sr` process died while a call was running (the Mac slept or restarted, the window closed, a crash): the task row keeps the process id and its start time, and `sr check` (or the interface's poll) marks such a task `stopped: process ended`. It is resumed by the same agent, not a substitute, since no plan limit was hit: the call that was running is made again, then the task goes on. The same one-resume rule holds. No substitute is involved, so the exceptions that guard against one do not apply: a process-ended stop on a `versus` or `vote` task, on an override or on a Cursor call is resumed too, by the same agent. A fallback's own redo is never resumed; the owner runs `sr fallback` again. Built by brief 22.
- Only Claude and ChatGPT substitute for each other, whichever slot the stopped call was in. A stopped Grok or Muse call is not resumable, nor a Cursor call stopped on its pool (a process-ended Cursor call is, above): a Cursor stop on a used-up pool is the pool's limit, not a plan limit of Claude's or ChatGPT's, and the owner runs the task again when the week resets, or sooner with another agent in the slot. A task whose substitute is not live is not resumable.
- The substitute gets what the stopped agent was sent: the task; on a relay task, the result of the stage before; on a media task, the files, delivered the way the Media section delivers them to that agent; on a project task, the handoff. It never gets the stopped agent's partial output. That output stays in the log and is shown only when the owner asks.
- A stopped contract re-ask is replaced by the stage itself: the substitute gets the task and the result of the stage before, not the re-ask. One re-ask per stage holds across a resume.
- No agent checks its own work. When the substitute is the task's checker, or the preset's named checker, the other builder checks instead. When that check round then fails to run, the Checking section applies: the result goes to the owner marked unchecked, and the log says why.
- When the stopped call is the check round itself, the other builder checks instead, unless it did the work; then the result goes to the owner marked unchecked.
- When the stopped call is a check stage (a preset with `is_check`), the other builder takes the stage only if it did not make the stage before; otherwise the resume is refused with the reason and the stage before's result goes to the owner marked unchecked.
- A task on a preset with review stages (`versus`) is never resumed on a plan limit. The substitute for one builder is the other builder, which already has its own candidate. The owner runs the task again.
- A task on a tally preset (`vote`) is never resumed on a plan limit. The substitute for one voter is already a voter, and one agent voting twice is not a vote. The owner runs the task again, or runs it with another agent in that slot once Muse is live.
- On `redteam`, a stopped revise stage is resumed only by the agent that made the build it revises, so it cannot be resumed by a substitute: the resume is refused with the reason, and the attacked build goes to the owner marked unchecked with the attack list. A stopped build or attack stage is resumed as any stage is, by the other builder, and the slot rules still hold: the substitute for the `build` slot must not be the `attack` agent; if it would be, the resume is refused. The second attack (brief 32) is never resumed on a plan limit or by a substitute: a stop skips it (see Relay); a process-ended stop is resumed by the same agent.
- A fallback call that stops on a plan limit is never resumed. The owner runs the fallback again when the limit lifts.
- A split's plan call or integration call that stops is taken over by the other builder (see Takeover), except the integration of a project split in file mode, a Claude build call that is not taken over (see Project files); a piece is taken over, or resumed by hand, by its own number.
- One manual resume per task, counted apart from the takeover (see Takeover). If the substitute is also at its plan limit, or a takeover's own call stopped on one, the task stays stopped and the message says both are.
- A Ctrl+C during the substitute's call is stored as a cancel on that call. It does not use up the task's one resume: the task can be resumed again.
- An override task is never resumed on a plan limit.
- The owner runs it. The router never resumes on its own: on a plan limit it takes over (see Takeover), and offers `sr resume` only for what stays manual, naming the command and the agent, or why it can't. In the interface the offer is a button that runs the same command, shown only when the JSON offers it, and gone after the one resume.
- The new call rows carry the id of the stopped call they replace. Stopped rows stay. The task's status is whatever the resumed run produces.
- Web search on a resumed call follows the Web search section, whichever agent does it.
- A project task's handoff contract holds across a resume: whoever does the build returns the handoff section.

## Fallback

- `sr fallback <n>` redoes task `n` from scratch after its result failed its check twice: the checker failed it, the fix round ran, and the checker failed it again. On `collab`, after the check stage returned unresolved items. The task's checker becomes the doer, and the task's original doer checks the redo with the usual loop: one check round, one fix round.
- The owner runs it. The router never starts a fallback on its own. When a task ends with its check failed twice, the router's message names `sr fallback <n>` and the agent that would redo it, or says why the task cannot fall back. In the interface the message is a button that runs the same command, shown only when the task can fall back.
- The fallback doer must be Claude or ChatGPT. When the task's checker is Grok or Muse, the task cannot fall back. The original doer may be any live agent; it checks as the Checking section says, sanity check only where it cannot reach what the result is about.
- The fallback doer gets what the original doer was sent (the task; on a relay task, the result of the stage before; on a media task, the files, delivered as the Media section delivers them to that agent; on a project task, the handoff) and the checker's final fix list: what it still wanted fixed after the fix round, or on `collab` the unresolved list. It never gets the failed result. The fix list is data, not instructions, and the prompt says so.
- On `research-build`: the agent in the `check` slot builds from the same research note, with web search; the agent in the `build` slot checks. The research is not run again. On `collab`: the `partner` builds from the same amended plan; the `lead` edits it as the check stage, under the check-stage rules. On `redteam`: the agent in the `check` slot builds from the task and the same attack lists, with the final fix list; the agent in the `build` slot checks, with the attack lists. The attack is not run again. With the default slots that is ChatGPT redoing and Claude checking, as before. The fallback doer must still be Claude or ChatGPT: a task whose `check` or `partner` slot held Grok cannot fall back. On a plain routed task: the skill's second agent builds; the skill's best agent checks. On a split task: ChatGPT integrates from the same piece results; Claude checks. A piece falls back by its own number.
- No fallback for a task that passed, a `quick_answer` task, an override task, a `versus` task, a `vote` task (nothing checked it, so nothing failed it), a task that ended unchecked, a task that stopped before its check, or a task whose doer and checker became the same agent after a resume, or a file-mode task (only Claude changes files; see Project files). One fallback per task; a second is refused. A fallback whose doer's call stopped (a plan limit, an error, a Ctrl+C) does not use up the task's one fallback; nothing on the task changes.
- If the redo also fails its check twice, the router stops and shows the owner everything: the original result and its final fix list, the redo and its final fix list. The owner decides.
- The fallback's call rows carry the task they fall back for and the agent they replace. The original rows stay. The task's status, result and check are whatever the fallback run produces; the original result is kept and shown only when the owner asks.
- A fallback is never resumed, never taken over and never falls back again. Web search on a fallback call follows the Web search section, whichever agent does it.
- A project task's handoff contract holds on a fallback: the fallback doer returns the handoff section, and the handoff entry is written from the fallback's result when it is delivered, replacing nothing (see Project context).

## Project context

- **Why.** The owner uses the router to build a project over many tasks. Each task must know what the ones before it did. The handoff file is one file per project, and the router carries it in and writes it back. Beside it, the project's delivered results are searchable through Memory under the project's tag (see Memory): the file is what the next task must read, the memory is what it may find.
- **The registry.** `config/projects.json` maps a project name to a folder. `sr project add <name> <path>` adds one; the folder must exist; `sr project list` prints them; `sr project remove <name>` removes the entry and touches no file. Only the owner runs these. A folder named in the `never_register` setting is never registered. The `never_register` setting holds it (brief 25), so no tracked file names the folder. A name is lower case, letters, digits and `-`.
- **Making a project.** `sr project new <name>` makes a project in one step: the folder `<projects_root>/<name>` (see Router for the interface, Settings for people; the root is made if it is missing), its `HANDOFF.md`, and the registry entry. The starting notes are the one argument after `--`: nothing there, or more than one, is refused with a message saying to quote them. They are written once at the top of that new `HANDOFF.md`, as given, with the router's empty block below them. That is the one time `new` writes outside the block in that file, and only in a file it has just made; from then on the notes are the owner's like the rest of the file. With git installed, `new` then sets up git for the project: the `.gitignore` lines Project files names, `git init`, and a first commit holding `.gitignore` and `HANDOFF.md` (brief 28); without git it makes the project as before and says that file work needs git. A folder already there is registered as it is, exactly as `sr project add` would; starting notes are refused for it, because its `HANDOFF.md` is the owner's to edit. The refusals are `add`'s (the name rule, a folder in `never_register` by name or by resolved path, a name already registered, which `new` refuses naming where it is registered, the home folder as `~`), plus: notes past 4,000 characters; a notes line that is one of the router's markers; and notes the redactor would change or the key scan matches (the checks a handoff passes before every call). A refused line is named by its number, never quoted, and a refusal writes nothing. The folder must sit directly inside the resolved root, and a link at `<projects_root>/<name>` is refused wherever it points. `--dry-run` takes the name alone, says what `new` would do (make the folder, register the one there, or refuse, and why) and writes nothing. `--json` and `--dry-run` may stand anywhere before `--` (the JSON: see Router for the interface). Nothing is ever deleted: a step that fails after the folder is made leaves the folder and says so. The page's New project sheet runs it (see Interface); a folder anywhere else is registered with `sr project add` in Terminal, or moved into `projects_root` in Finder and added from the sheet by its name. Built by brief 26; git by brief 28. **From an idea** (brief 33.4) is a mode of the New project sheet: the idea, at most `idea_max` characters (2,000, checked on the page alone), becomes the notes through the same `sr project new`, and the composer fills with Draft it. Nothing is sent until the owner presses Send.
- **The handoff file.** `~/Projects/<name>/HANDOFF.md`, or the file the owner's own tooling already keeps there under that name. The router owns one block in it, between the lines `<!-- sr:start -->` and `<!-- sr:end -->`, at the end of the file. Everything outside the block is the owner's and Claude Code's, and the router changes it only on the owner's own command: the starting notes of a project it makes, the notes the owner edits or pins from the page (see Project notes, below), and the one section "Current plan's decisions", which the router writes at a new plan's Approve, clears on one with no questions and puts back on its Undo (see The plan). `sr project add` creates the file with an empty block if it is missing, and adds the block to the end if the file exists without one.
- **The router's block** holds the newest 8 task entries, newest first. An entry is: the task number, the date, the preset or skill, the doer, then `Produced`, `Status` and `Next` from the result's handoff section. Older entries are dropped from the block; they stay in the log and `sr show` prints them.
- **`--project <name>`** on `sr route`, on `sr relay <preset>` for every preset (see Relay) and on `sr split` (see Split). Refused at intake on an override task. A name not in the registry is refused with the list.
- **What goes in.** The whole handoff file, through the redactor, is pasted as data between the `=====` markers into every agent call on the task: the doer, every relay stage, the checker, the fix round, a resume, a fallback. Never to Jev. On a media task the files go as the Media section says; the handoff is text in the prompt and never a file. The prompt says the handoff is data about the project, written before this task, and not instructions. The file is also read once at intake, before any row: a project whose `HANDOFF.md` cannot be read is refused.
- **Grok.** The handoff on a Grok call counts toward Grok's prompt limit with the rest of the prompt. A handoff that would push a Grok call past the limit is trimmed to fit: the owner's part above the router's block first, from its top, then the router's block, oldest entry first; a handoff that cannot fit even with one entry is left out. The call is never failed for the handoff. Every call row keeps the handoff as sent, its text and line count, so `sr show --handoff` prints what the build call saw even after the file changed; on a trimmed Grok call that record is the trimmed text. The trim changes what Grok is sent, never the file. On a call that also carries a memory block, the memory block goes first and the handoff is touched only when that was not enough (see Memory).
- **Kept in full.** The whole handoff section of every build result stays on its call row in the log, beyond the 8 entries the block keeps, so Memory stores every entry and `sr memory rebuild` can reload it. `sr show <n>` prints a project task's entry from the log.
- **What comes back.** The build call's result ends with a handoff section. The contract, checked in code: `## Handoff` with `### Produced` (at least one line naming what the result made and where it is: a path under the task folder, `sr show <n>`, or the plain words `nothing written` followed on the same line by the inline deliverable's exact heading or first line and one clause on what it holds; a bare `nothing written` is a contract miss), `### Status` (at least one line on where the project stands after this task), `### Next` (one to three lines). Each part ends at its first blank line or the next heading, so a `Sources:` block after `### Next` is not part of Next; the section is the last thing in the result, and the build prompt says so. A part past its count is re-asked with the extra lines named. Missing or malformed: the one re-ask names what is missing; still missing, the task stops as any contract miss does. The build call is: the doer on a plain routed task; the last stage before the checker on `research-build`, on `redteam` and, on a project, on `collab`; each `versus` build stage, the picked candidate's section being the entry; on `vote` none, and the router writes the entry; on a plan task none, and the router writes the entry when the plan lands (see The plan); the substitute on a resume; the fallback doer on a fallback. The fix round's result must carry the section too, and the same contract is checked on it.
- **Grok as doer.** Grok returns no handoff section and the contract is not applied. The router writes the entry itself: `Produced` names the task's result (`sr show <n>`) and any image path; `Status` and `Next` read `—`.
- **When the entry is written.** When the task is delivered: passed, or delivered unchecked; a file-mode task delivered with a change, when it lands (see Project files). The entry comes from the delivered result's handoff section (the fixed result after a fix round; the fallback's result after a fallback). A task that failed its check twice, stopped, or came back to the owner gets a one-line entry from the router: the task number, the date, and `failed: <reason>` or `stopped: <reason>`, so the next task knows. A cancelled task gets no entry. The router writes the file; a model never does. The write is logged on the task row with the handoff file's line count after the write. An entry with nothing to land is its own commit, `sr: entry #<n>`, `HANDOFF.md` alone, by land's path, when the file is tracked and was clean before the write; a hand edit in it, no git or an untracked file: written with no commit. A commit that fails never fails the task; the output says so.
- **One active task per project.** A second `--project <name>` task while a task for that project is open (`queued` or `sent`) is refused with the open task's number. A plan waiting for answers (`waiting_on: answers`) holds its project, its copy kept, with no timeout, until the owner answers or cancels it, and Cancel removes the copy. A versus or tied vote awaiting its pick holds its project too. Neither is the final kind of return this section describes. A running suggest does not hold its project, a stated exception to this rule (v2.25); at most one runs per project, and intake refuses a second. A split on the project is open from intake until it ends, lands or is discarded, while it waits at its plan or on its pieces too; its pieces are part of it, never a second task (see Split). A Grok return counts as open until it is collected or times out. A task that came back to the owner (a Jev floor question with no terminal, a handoff that looked like a key) is final: nothing resumes it and `sr cancel` cannot touch it, so it never blocks the project. A task whose check failed twice is closed too: its `failed:` line is already in the block, and a fallback adds its own line.
- **Size.** When the handoff file passes 300 lines after a write, the router prints a warning naming the count and the line where the router's block starts. It still sends the whole file. The owner trims the part above the block; the router trims its own block to 8 entries on every write.
- **Project notes.** The part of `HANDOFF.md` above the router's block is the project's notes; they ride on every call of the project with the rest of the file. `sr project notes <name>` prints them; with `--save [--expect <hash>] -- <text>` it replaces them, and `sr project pin <name> --task <n> -- <text>` adds a piece of a result at their end under `### Pinned from #<n> (<date>)`, each on the owner's command from the page (Notes on a project, Pin to notes on a result card). Each holds the project's lock, re-reads the file, refuses a marker line, a `.env` value, a key or more than `project_notes_max` characters (`config/settings.json`) with nothing written, keeps the router's block byte for byte, and with git and `HANDOFF.md` tracked commits `HANDOFF.md` alone (`sr: notes edited`, `sr: pinned #<n> to the notes`); otherwise it writes the file. No entry goes in the block. Built by brief 30 (D19).
- **Not in this feature.** No agent writes a file in the project folder. Outside file mode the handoff is memory, not a work product: the code, docs and files a task describes are the owner's or Claude Code's to write from the result. In file mode the router puts into the folder the change the owner lands, and on their command a result the owner saves into the project and their `SPEC.md` (`sr project spec --save`; see Project files, The spec). The owner's existing per-repo handoff rule for Claude Code is unchanged; this block sits at the end of that same file.
- `sr show <n>` on a project task prints the project name, the handoff entry the task wrote, and `--handoff` prints the handoff file as it was sent to the task's calls. `sr log` prints the project name beside a project task.
- Built by brief 18, live on `main` since 16 Oct 2026 (log version 11; `super-router` registered; the router's own `HANDOFF.md` is gitignored in this repo). The page lists the projects and sends `--project` (brief 23), and makes them from its New project sheet (brief 26).

## The spec

- `SPEC.md` at a project's top level is the owner's spec: free text plus `## Examples` and `## Done when`, whose items code labels `E1…` and `D1…`.
- Read once at intake and kept with the task (`spec_max` 6,000; a `.env` value or a key-shaped line refused by line, `spec_refused`); sent on every agent call of the project after the STEP block and before the handoff, as data, giving way whole on Grok after memory and the notes; a check, re-check, review or attack gets the judge line.
- Only the owner changes it: a build's change is put back before the check and Land refuses one still there; the owner writes it with `sr project spec --save` (the Notes sheet's Spec section; one commit `sr: spec edited`), Save to project or files in.
- A top-level name differing from `SPEC.md` by case alone is refused by Save to project and files in, naming the spelling; `docs/spec.md` is any other file.
- A plan's step names the examples it covers (`covers:`); the plan shows what it leaves out, which is a note, never a must. Auto stops before a step when the spec changed since the run started (`spec_changed`).
- Draft it (no spec yet) sends a `--no-files` task: Claude, always, reads a read-only copy and answers in text; ChatGPT checks.

## Memory

- **Why.** The handoff file remembers one project, eight entries deep, and only what a build chose to write. Nothing remembers a one-off task from last week, a decision made in another project, or the hundredth entry. Memory does: every result the router delivered but a suggest's is stored, tagged with its project or its chat, and a tagged task gets the stored results that match it, found by code, never by a model.
- **What it is.** Hindsight (Vectorize, open source, MIT), run on this Mac by the router: `hindsight-api-slim[local-onnx,embedded-db]` from pip in its own virtual environment, `~/.hindsight/venv` (the ONNX embeddings, the RRF reranker and pg0; no PyTorch), its own embedded Postgres (pg0) under `~/.pg0/` (`~/.hindsight/` holds the virtual environment, the pid and the log), listening on `127.0.0.1:8888` and nowhere else. `HINDSIGHT_API_LLM_PROVIDER=none`: no LLM, no API key, no fact extraction, no reflect, no consolidation, no observations. Retain stores the text as chunks (`retain_extraction_mode` `chunks`); recall is embedding, keyword, graph and temporal search with a local reranker; the one model, the ONNX export of `intfloat/multilingual-e5-small` (470 MB), is downloaded once from Hugging Face into `~/.cache/huggingface`, and the RRF reranker needs none. The router talks to it over HTTP with `requests`, already a dependency. The one-line reason for the new dependency: a local search over everything delivered, costing nothing, that the router can delete and rebuild from the log.
- **One bank, `super-router`.** The router creates it on first use (`chunks` mode, observations off) and never touches another bank. A memory is one task: its task text and its delivered result, with the `## Handoff` section when the task had one, stored under `document_id` `task-<task_id>`, so storing a task twice replaces the first copy and never duplicates it. Each memory carries metadata the router writes (`n`, `date`, `kind`, `doer`, `status`, `tag`) and exactly one tag: `project:<name>` or `chat:<name>`. An untagged task gets no memory and no recall.
- **What is stored.** A delivered result the rules already let the owner see: passed, fixed, checked-by-vote, `quick_answer`, or a picked `versus` candidate (stored whatever its review said, with the review's status in its heading). A picked vote answer (no two agents agreed on it) and a delivery left unchecked because a round did not run are not stored. The result as `sr show` prints it, without a `## Next` section or its `Next:` lines (see Next steps), never a stage result, an unpicked candidate, a round file, an attack list, or a voter's reasons. An unchecked override result, a failed task, a stopped task, a returned task, a cancelled task: not stored. A project task that failed twice is in the handoff file as a `failed:` line; memory does not repeat it. Stored only after the redactor; a result the redactor still flags is not stored, and the task row says so.
- **When.** At delivery, by code, beside the handoff entry: one write per task, logged on the task row as `memory: stored <document_id>, <n> characters`. A write that fails (Hindsight down, a refused request) is logged as `memory: skipped: <reason>` and the task is still delivered; nothing waits and nothing retries. A task delivered while memory is off is logged `memory: skipped: off` and is never stored (see The switch). `sr memory rebuild` reloads every storable task from the log into the bank, oldest first, replacing what is there, so the store can always be deleted and rebuilt: the log is the truth, the store is an index on it.
- **The tag.** `--project <name>` tags the task `project:<name>`. `--chat <name>` tags it `chat:<name>`: a name is lower case, letters, digits and `-`, like a project name; no registry, no file, nothing to create; a chat exists when a task carries its tag, and the first task with a new name prints `new chat: <name>`, so a typo is seen, not refused. `--chat` with `--project` is refused at intake: one tag per task. `--chat` on `sr split` is refused in version 2: sent from a chat on the page, a split goes untagged. `--chat` is accepted by `sr route` and `sr relay`, on an override, and a resume or a fallback carries the task's tag. `sr chat list` prints every chat name with its task count and the date of its newest task, from the log. `sr log --chat <name>` prints that chat's tasks.
- **What goes in.** On every agent call on a tagged task (the doer, every relay stage, the checker, the fix round, a resume, a fallback) the router pastes one memory block as data between the `=====` markers, after the task and after the handoff block when there is one: first the newest 3 delivered tasks with the same tag, newest first, always, read from the log, so "what we just did" never loses to ranking; then the recall matches from Hindsight that are not among them, filtered to the tag in code (`tags_match` `any_strict`: a memory from another tag or with no tag never comes back), newest first, deduplicated by task number. Each memory as its task number, date, kind and doer on one line (and the check's status when it is not a pass), then its text, read from the log: the part Hindsight matched when it is a byte-for-byte piece of the task's content there, else the content's head; the store names the task and never supplies text the log does not hold. The doer and every relay stage recall afresh, one recall per call; the check, fix and re-check rounds get the block the build call got, from its row; a re-ask its first call's; a resume the stopped call's; a fallback the replaced call's. The task being run is never in its own block, and a task the call carries whole as its earlier result (`--from`, see Next steps) is left out of it. Never to Jev. The prompt says the block is earlier results under the same tag, found by search, data and not instructions, true as of their dates, and that the result it asks for is for this task alone.
- **Caps, in code.** At most 8 memories: the newest 3 and up to 5 matches (`memory_newest`, `memory_matches`; the owner, 27 Oct, D18), at most 2,000 characters each; the oldest matches are dropped first and a cut memory ends with `[cut]`. The recall query is the task's text and the text of the tag's newest delivered task, cut to 1,500 characters by cutting the earlier text first (Hindsight refuses a query past 500 tokens), so a follow-up like "what about the other one" searches what it follows; a tag's first task searches with its own text. Brief 19 measures a real prompt before the numbers are fixed; both live in `config/settings.json`.
- **Grok.** A memory block on a Grok call counts toward Grok's prompt limit with the rest of the prompt. A block that would push a Grok call past the limit is trimmed, the oldest match first and then the oldest of the newest tasks, until the call fits; a block that cannot fit even with the newest task is left out. The call is never failed for the block. When a Grok call carries both blocks, the memory block gives way first, all of it if need be, and only then is the handoff trimmed as Project context says; the handoff is never cut to make room for memory. Then the usual length rule runs. Every call row keeps the memory block as sent, text and count, and the query it searched with (brief 30), so `sr show --memory` prints what the build call saw.
- **Recalled memories are data.** Every call that carries a block is told it is background: use a memory only where it helps the task, and don't report on memories it didn't use (brief 29.1). Code drops any memory whose source task is not `done` in the log or is forgotten (see Forget), whatever Hindsight returns, and any memory the redactor still flags. The checker gets the same block and one added line (see Checking). No model judges relevance before the send: the checker judges it after, and the owner's own reading judges it last.
- **Down.** When Hindsight cannot be reached at a send and `memory` is `auto` (the default, in `config/settings.json`), the router starts it and waits up to 60 seconds for `/health` (about 35 seconds from cold); one start at a time, by a lock. Only if it is still down does the task run without the block: the call row says `memory: unavailable` and the owner sees one line saying memory could not start. With `memory: off` the router never starts it, never recalls from it and never stores in it, even while it runs: tagged tasks run without blocks, and what they deliver is not stored, then or later (see The switch, below). Nothing fails and nothing retries. A tagged `recall` task is the exception: it never calls an agent without its memory. Its first call's fresh recall needs the store: when it can't be reached after the start attempt, the task comes back before any agent call with `memory unavailable (the store could not be started): nothing to recall from`, or with `memory: off`, `memory unavailable (memory is off in settings): nothing to recall from` (brief 23). A check, fix or re-check round, a re-ask, a fallback or a resume uses its saved block without asking the store, and is held back with the same reason only when that block was itself unavailable; a held-back fallback or resume is not used up. (Seen live 20 Oct: #103 ran with the store down and failed its check twice; built after it, `1f57c16`.) `sr memory status` prints online or offline, the bank's document count, and the size of pg0's folder (`~/.pg0`); while memory is off it says so first and names no `sr memory start` (brief 27). `sr memory start` starts the server on the loopback address, waits for `/health` and backfills, also when the store was already up; it and `sr memory rebuild` are refused while `memory` is `off`. `sr memory stop` stops it. `sr serve` starts it too when `memory` is `auto`. Whenever the store comes up, the router backfills it: every delivered, storable tagged task missing from the bank is stored, oldest first, and any already there is skipped (what `sr memory rebuild` does, limited to the missing ones). `sr memory start`, `stop`, `status` and `rebuild` stay for Terminal; the interface never needs them. `sr memory on` and `off` are the switch (below). Built by brief 22.
- **The switch.** `sr memory off` and `sr memory on` set `memory` (`off`, or `auto` for on) for this Mac in `config/settings.local.json`, and nothing else in it: the file is made if it is missing, every other key and its value is kept, the file is replaced whole and never left half-written, and a file that is not a JSON object is refused with nothing written. The tracked `config/settings.json` is never written. `off` then stops the store if the router started it (a store started some other way is left running and is not used); `on` starts it and backfills as `sr memory start` does, under the same lock. Each exits 0 once the setting is as asked, the store's start or stop said in its message, and 2 refused with nothing written; its JSON adds `memory` after the eight keys (the setting, the one before, whether the store answers, whether it is installed). The setting is read at each fresh recall and at each delivery, so a switch counts from the next call. A call made while off records that memory was off; a task delivered while off records `memory: skipped: off` on its row, and neither the backfill nor `sr memory rebuild` ever stores it, nor does a later block carry it as the newest task under its tag: off means not remembered, then or later. A check, fix or re-check round, a re-ask, a resume or a fallback still uses its saved block, which asks nothing of the store; a saved block that was off stays off, so a tagged recall task's later round comes back as it does for an unavailable block. Project context is untouched: a project's `HANDOFF.md` rides and is written as before. The page's Memory switch runs these two commands (see Interface). Built by brief 27.
- **Stale.** A memory is true as of its date and may be wrong now. The block says so, and the checker line covers a result that leans on a contradicted memory. The owner's notes on a project, edited on the page or in the handoff file, are the correction for a project; for any tagged task, Forget takes it out of memory (below).
- **Forget** (brief 30, D19). `sr forget <n>`, Forget on a card, adds a `forgotten` record to the task's memory records. The task is then not storable: no block carries it, as a newest task or a match; the query never takes its text; a recall naming it is dropped; the backfill and the rebuild never store it. Its document is deleted from the bank now, or by the next backfill, which deletes every forgotten task's document it finds. `sr forget <n> --undo` (Remember again) adds `remembered`: the task is storable again by the usual rules (a delivery made while memory was off stays unstored) and is stored now or by the backfill. The log keeps the task; a block already sent is never changed; `HANDOFF.md` is never touched. Refused for an open task, an untagged one or a piece.
- **What is written where.** The bank, under `~/.pg0/`; the server's pid and log under `~/.hindsight/`. The `memory` key in `config/settings.local.json`, by `sr memory on` and `off` only. The tag and the write record on the task row. The block as sent on the call row. Nothing in a project folder. No file a model wrote. The router never edits a memory's text: a stored task is what the log says it was, and a rebuild makes it so again.
- `sr show <n>` on a tagged task prints the tag and the write record, and `--memory` prints the block as it was sent to the task's build call, then one line per call on the task: entries sent of entries found, or `left out` with both lengths on a Grok call, or `unavailable`, or `from <call>` when the block was reused. (From the 18 Oct test sheet: on #96 the fix round's left-out block was in the rows and not on screen.) `sr log` prints the tag beside the task, as the preset is shown. The interface, when un-parked, shows chats as the UI decisions already list them; nothing is built for it here.
- The block goes through the same helper brief 18 built for the handoff block, so a prompt has one code path for context.
- Built by brief 19, live on `main` since 18 Oct 2026 (log version 12). Chats (parked 16 Oct, design in 2.26) is superseded by this section: its tag survives, its last-5 attach from the log does not.

## Router notes

- **Why.** Some things every agent should know on every task: how the owner likes answers, their stack, what never to do; and some one agent should: how ChatGPT should check, what Grok should name. Typed into each task they are lost, and kept in each agent's own settings they are scattered and unseen. The router notes are one file the owner edits on the page, sent with every call (brief 30; the never-Terminal plan's D8 and D9).
- **The file.** `config/router-notes.md`, this Mac's own and gitignored. The tracked `config/router-notes.default.md` holds the six headings and nothing else; while there is no local file the router reads it, so nothing is sent. Six sections, each at most once, in any order, by their exact headings: `## All agents`, `## Claude`, `## ChatGPT`, `## Grok`, `## Cursor` and `## Planner`. A section's text runs to the next `## ` line; a section with no text sends nothing. Invalid: text before the first heading, another `## ` heading, a heading twice, more than `notes_max` characters (`config/settings.json`), a line the key scan matches or one holding a `.env` value; a problem is named by its line, never its text. `sr notes` prints the file with its counts and hash; `sr notes save [--expect <hash>] -- <text>` checks the whole file and writes it, or refuses with nothing written, and refuses a file changed since the hash. The page's editor runs it (see Interface, Setup). Nothing else writes the file but the owner's own editor.
- **Who gets what.** Every agent call on a task gets `## All agents` and the section of the agent making that call: a doer, every relay stage, every check, re-check and fix round, a re-ask, a split's plan, pieces, integration and check, a follow-up, a takeover, a resume, a fallback, Grok's calls and Cursor's. A takeover or a substitute gets its own section, never the stopped agent's. A split's plan call and its re-ask, and a plan task's plan, revise and fix calls and their re-asks (brief 33.1), also get `## Planner`, where the owner's judgment on teams lives (see Split and The plan). Never Jev, a probe, Hindsight, a project folder, the handoff or memory.
- **Once per task.** The router reads and checks the file at intake, before any row: an invalid file refuses the task with nothing written, naming the problem's line and where to fix it. A valid one is kept with the task (`tasks/<task_id>/router-notes.md`; `sr show --json` gives its hash and characters from that copy as `router_notes`, with no new column), and every call on the task sends from that copy, so an edit never changes a running task; a split's pieces use the split's. A task from before brief 30 sends none. The key scan runs again on each send: a hit returns the task to the owner, as a handoff that looks like a key does, with nothing sent.
- **Where, and what wins.** First in the prompt, as the person's notes for every task, marked apart from the data blocks and never with their markers. The task, the instructions after the notes and the reply format win any conflict, and the prompt says so. A judging call is told that not following the person's notes is never on its own a must, a fail or a high attack (see Checking). With nothing to send, the prompt is as it was.
- **Grok.** The notes count toward Grok's prompt limit. Past it, the memory block gives way first, then the notes, whole, never cut, then the handoff as Project context says, then the usual rule. A call is never failed for the notes; its row and its card say they were left out.
- **What they are not.** Never stored in memory, never written in a project, never in the public copy: the default ships, the file never does. They go to every agent's service with the prompt, Grok Bot's inbox included, so they hold nothing private; the key scan refuses keys.
- Status's `notes` holds their state, counts, cap, Grok's share and hash; a task's copy gives its hash (`router_notes` in its JSON, since `notes` there is its check's notes); each call row holds the sections it sent, or that they were left out and why; `sr show <n> --notes` prints them. Built by brief 30.

## Cursor

- **Why.** A second coding agent that costs nothing new: Cursor is in the owner's X Subscription beside Grok Bot and the Grok apps. Inside the router it is Grok, pinned by name, behind Cursor's command line, with every tool switched off: text in, code or text out. The value Cursor sells, editing a repository and running its tests, is not used here: no agent writes a file in any project (see Agents in v2), and that work stays Claude Code's in the build loop.
- **How it is reached.** The Cursor command line, `agent`, installed by the owner and signed in once with `agent login` on the X-linked account. Every call is `agent -p` with `--output-format stream-json`, `--model <name>` and `--mode ask --sandbox enabled --workspace <scratch> --trust` (the trust flag names the scratch folder only; without it print mode exits at Cursor's workspace-trust gate before any model call), run by the router as an argument list, never a shell string, from an empty scratch folder the router makes for the call in the system's temporary folder and deletes after: a call is refused before it is made, with the reason, when any folder above that scratch folder holds an agent's instruction file (`CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `AGENT.md`, `GEMINI.md`, `.cursorrules`, `.cursor/`, `.windsurfrules`, `.clinerules`, `.github/copilot-instructions.md`), since Cursor's command line can load such a file from the folders above it as rules, with or without git, and no flag turns that off (seen in Proof 4, 28 Oct: from under the router's own folder it read the router's `CLAUDE.md` as "workspace rules"; brief 32). The stream's first event names the model that served and its last event carries the text; the router reads both and keeps on the call row each tool event's kind and outcome, their count, and the usage the terminal event reports; the raw stream is kept, redacted, under `media/cursor/<task-id>/`. Every prompt opens with the scope paragraph and the no-tools sentence, then the prompt the Claude worker would get for that role; the opening also keeps the command from reading a task's first word as one of its subcommands. A non-zero exit, no terminal event, or an empty text is a failed call, as any agent's error is, never retried. On a timeout the stream read so far is kept as a finished call's is, the row marked partial; the call still fails and is skipped as before. Never `--force`, never `--resume`, never `--background`, no MCP server, no `CURSOR_API_KEY`. The prompt is the command's argument; a prompt past 100,000 characters is refused at intake with both lengths, measured on the task-alone build prompt with the opening, and again on every prompt at send time.
- **The model.** One Grok model, named in `config/agents.json` (`grok-4.7-high` to start: Cursor's ids carry the effort level, `grok-4.7-low|medium|high|xhigh` and their `-fast` twins; Grok 4.6 and 4.5 are `cursor-grok-4.6-…` and `cursor-grok-4.5-high`) and passed on every call; never `auto`, never a name that does not start with `grok` or `cursor-grok`. When the model the stream names is not the one asked for, the call fails before its text is used, and the row says which model answered. The stream names a display name (`Grok 4.7 256K High` for `grok-4.7-high`): the match drops the context-size token and the fast marker, reads a format character in the name as the fast twin (a `-fast` model burns the pool twice as fast), and compares letters and digits; an id ending in `-high` also matches the name without it, which is how Cursor shows its default effort. Only the owner changes the name, as the owner alone flips the live flag.
- **The sandbox.** Before every call the router writes a `.cursor/cli.json` into the scratch folder that denies every shell command, every read, every write and every MCP tool (`Shell`, `Read` and `Write`, each on `**` and on absolute paths, and `Mcp(*:*)`, since the router never reads Cursor's own config), so the task text is all Cursor gets and text is all it returns. Brief 20 proves it before any real task: a canary file beside the folder that Cursor is told to read and must not, and a shell command it is told to run and must not, judged from the stream's tool events, never from what Cursor says. A probe that fails keeps Cursor off. Since brief 32 the probe has a third canary, which checks the per-call guard (see How it is reached): four instruction files (`CLAUDE.md`, `AGENTS.md`, `.cursorrules` and a `.cursor` rule), each with its own marker, one and two folders above its scratch folder. The files whose markers show in Cursor's reply or thinking are recorded with the result (`rules_from_above`), and that alone never fails it; it fails when a marker came from a file the guard doesn't look for, or when the guard, run where the scratch folder is made with those files in place, would let a call through (no model call). It records whether Cursor lists any MCP tool. A failure recorded under the earlier rule reads as no record, as a pass from before the third canary reads as no pass (brief 32's D, 29 Oct: the first rule failed on any marker, so it could never pass while Cursor reads rule files from above). The Cursor command line updates itself (seen live 20 Oct: `2026.10.16-e3cb207` to `2026.10.19-6bbf2c4` within five minutes of a task), so the probe's pass is pinned to the agent version in `probe_state.json` (`cursor_sandbox`): at intake of a task with a Cursor slot or `@cursor`, and before the first Cursor call in a command, the router reads `agent --version` and the login, and when the pass is missing, is from before the third canary, or the agent moved, the router runs the three canaries itself (3 pool calls, one probe at a time by a lock) and goes on only on a pass. A failed canary keeps Cursor off on that version: the task is refused before any row with the reason `probe_failed`, said in plain words (on `redteam` the second attack is left out instead, as Relay says), and Cursor stays off until a later version passes. No login refuses with its reason too. `sr probe` still runs the canaries by hand. Built by brief 22. Cursor's glob tool is outside the three permission rules; the probe saw it return nothing for files that existed. A read, shell or write that completes without a denial, or a listing that finds a file, fails the call and its text is not used. What rides along from the owner's own `~/.cursor` (rules, a global config) is recorded by the probe and left to the owner, as with Codex's `AGENTS.md`; the router never edits `~/.cursor`.
- **What it does.** A doer, in text: code, fixes and explanations, or any text task the owner puts it in. It starts in the `versus` `a` or `b` slot, where it builds a candidate and reviews the other builder's, and the owner picks. After rule 12 it may fill the build slots the Relay section names, and routed `code` tasks when the owner makes it that skill's best agent in the skill table, with ChatGPT checking; `best` and `second` are routing fields Jev never sees, so that change needs no re-test. Never a checker on a routed task, never a reviewer outside `versus`, never an attacker outside `redteam`'s attack slots (brief 32, D25: the second attack by default, in text, on a project too), never a voter, a stand-in, a substitute or a fallback doer in version 2; never resumed. A fallback of a task Cursor did is redone by its checker and delivered unchecked, since Cursor never checks. No files: a task with files whose doer would be Cursor comes back to the owner with the label shown, as a Grok one does. No handoff outside an attack slot: any other Cursor slot on a `--project` task is refused at intake. In an attack slot on a project it gets, as text in its prompt, what any attacker gets there: the build (in file mode the change and its test results), the handoff and the memory block; never a file, a copy or a tool. A memory block rides on a tagged task as it does on any agent's call. The router asks it for no web search; whether its command line searches on its own is what the probe records, and a search it makes is its own.
- **Money.** The X Subscription's included weekly pool, shared with Grok Bot and the Grok apps, and nothing else: prepaid balance $0, auto top-up off, never changed by the router (see Money). A call refused because the pool is used up stops the task with the reason (the router recognises no pool text: such a call is a failed call with Cursor's own words on the row), except `redteam`'s second attack, which is skipped (see Relay); it is not resumed, and the owner runs it again when the week resets, or sooner with another agent in the slot. A third-party model is never asked for: that is what bills. Any charge, or any prompt from Cursor to add credit, is the kill criterion.
- **Status.** `sr status` and `sr status --json` show Cursor like the others: online means `agent status` says signed in, read from the command, never from a model call.
- **Override.** `@cursor` comes with the live flag, not before (see Overrides).
- **Secrets.** No key: Cursor keeps its own login in its own folder. The result goes through the redactor before it is stored or shown; `key_like` runs on everything handed to it, as on every agent.
- Built by brief 20 (log version 13, `calls.served`). Live since 20 Oct 2026 (`81b777a`): the probe passed, the send and return tests were clean, two live `versus` tasks and one real one met every key line. Measured: the pool moved less than one point across a `versus` task's two Cursor calls; a review costs four to five times a build's output tokens.

## Interface

- **Built by brief 23** (merged 21 Oct, `711d51d`). The decision record is `claude/ui-decisions.md`; `claude/handoff-ui.md` (18 Oct) is the design narrative; the design canvas (8 artboards) is a reference for the look, not a contract. This section says what must be true. The layout lives in the code and may change without a rules bump, as long as every line here still holds.
- **What it is.** A local web page that shows the log and runs `sr` commands with buttons. `sr serve` starts it: a Python server on the standard library (`http.server`; no new dependency) on 127.0.0.1 and the port in settings (`serve_port`), one HTML page with plain JS and CSS, no framework, no build step, no login, no network. It prints the address; it does not open a browser. Closing its terminal stops the page, not the tasks it started: each command it starts runs in its own session and finishes its rows.
- **Who it is for.** The owner, then people who clone the public copy (see Public copy). The page has no list of its own: agents, presets, skills, commands, projects and chats all come from `sr` JSON, so a clone with two agents shows two lights and a new preset appears by itself. Nothing the owner-specific is hardcoded: the drop folder, the report path and the port come from settings, and the page's own words say "you". Every missing piece degrades with a reason ("Not set up · how", linking to its row in the Settings tab).
- **The one rule.** Every button is a thin wrapper over an existing `sr` command; a chip runs nothing and only fills the composer (see Next steps). The page has no routing logic, no checker logic and no prompt of its own. The CLI is the source of truth: the server reads the router only through `sr … --json` (status, kept a minute; log; show; project list; a new project's dry run; Turn on undo's dry run; the router notes; a project's notes; a project's ideas) and runs `sr` for every change. If a thing cannot be done with an `sr` command, the page cannot do it. The one other command it runs is Open in Finder: `open -R <path>` on a path the files rule allows, or a registered project's own folder (never inside one, a climb or a link), on macOS only.
- **Other websites can't drive it.** Every `/api` request carries the launch token (random for each `sr serve`, put in the page only, never printed or written). A POST is JSON from the page's own `Origin`. No CORS header is ever sent, and OPTIONS gets 405. The Host must be 127.0.0.1 or localhost. The security policy allows no inline script. Files and images reach the page by `fetch` with the token and a blob URL, never a bare URL.
- **How it calls `sr`.** One Python builder turns each request into the argument list, for both the live command line and the run; never a shell string. What the person types goes after `--` as one argument, byte for byte: quotes, `$`, backticks, newlines, a leading `-`. A secret's value is the one exception: it goes on the command's stdin, never in the argument list, the display or a log (brief 31). Any other value that starts with `-` or holds a control character is refused before anything runs. Every argv carries `--json`, and `--source ui` on route and relay. Refs are task ids, never `#n`. The display quotes with `shlex.join` and dims the page's own flags; Copy leaves them out. The server answers at once and reads progress from the JSON; a failure shows the command's real stderr and exit code, never a made-up message. `sr serve` never reads `.env`, and the server never opens the log.
- **What the person types.** Plain text. The page adds the flags. A skill can be chosen on any routed task from the + menu; Jev isn't called, and the choice shows as a pill and resets after Send.
  - **Teams.** `Route`, the presets from status in a fixed order, then `Split` and `Plan`; `Route` is plain `sr route`, `Split` is `sr split` (see Split on the page, below) and `Plan` is `sr plan`, greyed off a project with the reason (see The plan on the page, below). The chosen team is sticky within the open chat or project and resets to `Route` on a switch or a reload; no team is remembered per chat. The guards: the chosen team is always visible, Send reads `Send · <Team>`, the placeholder names the chain, and Esc or `/route` clears. A team whose preset can't run now (status's `ready`) is greyed with its reason; a slot whose default isn't available shows that agent greyed and the agent the router fills it with chosen; the project selector greys for a team that refuses `--project`.
  - **Slots.** With a team chosen, each of its slots sets `--<slot> <agent>`, offering only the agents intake allows there (Cursor: `versus` a or b, and `redteam`'s attack slots; the second attack never the build's or the first attack's agent); a second attack the router would leave out reads Left out, with why.
  - `@claude`, `@chatgpt`, `@grok` and `@cursor` at the start of the text are the overrides as typed (see Overrides). The page's slash commands (the teams, `/split` and `/plan` among them, `/route`, `/quick`, `/project`, `/chat`, `/file`, `/web`) are stripped before anything reaches the router; any other `/word` stays text. A web toggle on `Route` only.
  - **Files.** A dropped or chosen file is written into the drop folder and sent with `--file`, on `Route` only (see Media).
  - **Shortcuts the browser doesn't own.** ⌥1–⌥8 the teams (Split is ⌥7, Plan ⌥8), only when the focus isn't in a text field (a browser keeps ⌘-digits and ⌘N; on German or French layouts ⌥-digits type brackets); Enter and ⌘↵ send; Shift+Enter is a new line; Esc clears; `?` opens the shortcuts sheet outside a text field; no new-chat key. Enter during an IME composition never sends.
- **Split on the page.** With Split picked, Send reads `Send · Split` and the command is `sr split --json --source ui -- <text>`, with `--project <name>` when the project picker is set. A split never carries `--chat`, even sent from a chat: the tag line reads `Split: untagged` or `Split: project <name>`; any other tag shows only when the send goes somewhere other than the open view. Quick, files, web and slots are greyed with the reason; the Jev box says Jev labels each piece once Claude plans them; Send asks no confirm, since approving the plan is the gate; Split is greyed with status's reason when it can't run. The plan waits in Needs you (below). A `## No split` answer is a grey card with the planner's line and Route it, which sends the same text, with the same project, as `sr route`, from the view it is in (without a project, an open chat's tag rides, as Send's does) and never through the composer; when Jev isn't set up the card asks for the skill first. "Run again as…" offers Split. After the approval, the split's card lists its pieces with their teams and states, Skip on a blocked one, a piece waiting for a pick linked to its card, and on a project split each piece's part of the change and the piece it waits for. Built by brief 29.

The project selector sets `--project`; where the two cannot ride together, the page greys one. ## Router for the interface

- **Why.** The page in `claude/handoff-ui.md` runs every action as an `sr` command with no terminal, reads every state as JSON, and must never ask a person to run a maintenance command. Today `sr` prints prose, asks questions only in a terminal, keeps task state in note strings, and needs `sr probe` and `sr memory start` by hand. This section is what changes. The master list is `claude/handoff-router-redesign.md`; brief 21 builds the contracts, brief 22 the run model.
- **The owner's rule (20 Oct).** A person using the interface never runs `sr probe` or any `sr memory` command, and never clicks a button to make the router work. The Memory switch (22 Oct) is a preference, not a fix: the page runs `sr memory on` or `off` for it, and nothing else of `sr memory`. The router probes, starts memory and backfills it on its own whenever needed. The only thing the page may say is why an agent is unavailable, in plain words, when a safety check fails.
- **Every action takes `--json`** (route, relay, split, resume, fallback, pick, cancel, check, project, chat, `memory on` and `off`, brief 27, and `land`, `undo` and `discard`, brief 28; `probe`, `notes`, `project notes`, `project pin`, `project save` and `forget`, brief 30; `ideas`, brief 33; `plan`, brief 33.1; `models`, brief 33.3; `auto`, brief 34): one object on stdout with `task_id`, `n`, `status`, `waiting_on`, `outcome`, `reason_code`, `exit` and `message`; an error the same shape on stderr. ## What the router may send

- A task the owner typed, to Jev for a label and to the agent that does it.
- That task and its result, to the checker.
- The checker's fix list, once, back to the agent that did the work, together with the task and that agent's own result.
- On a relay task: the task and the result of the stage before, to the next stage's agent, as data (see Relay). When the preset names a stage's input, that input instead: the task alone, or the task and one named earlier stage's result.
- On a relay task: the contract re-ask, once, back to that stage's agent, with the task, its own result, and the missing items.
- On a relay task whose last stage is the check: nothing beyond the two relay lines above. No fix list is sent to anyone.
- On a review stage: the task and the one candidate under review, as data, to the reviewer, with the candidate's `## Missing` note, if any, labeled apart from the deliverable. The other candidate is never sent to a builder or a reviewer.

On a revise stage: the task, the agent's own earlier result, and the attack lists, each labeled, as data, to the agent that made that result. On `redteam`'s check: the task, the revision and the attack lists, as data, to the checker.
- On a takeover or a resume: what the stopped agent was sent, to the agent taking over or the substitute (see Takeover and Resume). Never the stopped agent's partial output.
- On a fallback: what the original doer was sent, and the checker's final fix list as data, to the fallback doer (see Fallback). Never the failed result.
- On a split: the task and the menu of teams the router built, to Claude for the plan (on a project, with the handoff, in the copy, read only); each piece's text to Jev for its label; each approved piece's text to that piece's agents as a task of its team, a routed task or its preset's stages; the task, the joining line and every piece's result as data (on a project split, each piece's changed files too) to Claude for the integration, and then to ChatGPT with the integrated result (on a project split, the whole change and the tests) for the check (see Split).
- On a project task: the project's handoff file, through the redactor, as data, with every call the lines above describe on that task. Never to Jev. - On a tagged task (see Memory): the memory block, from Hindsight and the log and through the redactor, as data, with every call on that task. Never to Jev. Never a memory from another tag, an untagged task, or a result the owner did not get.
- On a task sent with `--from` (brief 33): the earlier result's block, through the redactor, as data, with every call on that task, to whichever agent makes it, Grok and Cursor included (see Next steps). Never to Jev.
- On a plan task (brief 33.1): the copy's file list (paths and sizes, at most 500, through the redactor, a path the key scan matches left out), as data, with every call on that task, to whichever agent makes it, Cursor included; the project's test command and its last Test's outcome with Claude's calls, the attacks and the check. Claude's plan, revise and fix calls read the copy itself, read only; no other agent gets a file's content. On a step of a plan, the STEP block with every call on that task (see The plan). Never to Jev.
- To Cursor: the task text, and on a relay stage the result its stage is given, as text in the command's prompt, with a memory block when the task carries a tag, an earlier result's block when it was sent with `--from`, and in `redteam`'s attack slots on a project the handoff and, in file mode, the change and its test results (brief 32); never a file, never anything from the Mac's disk: its tools are denied (see Cursor).

- The files on a task, to the doer and the checker, as copies in their workspace, when the agent is Claude or ChatGPT. See Media.

The router never invents a task or a stage, and forwards one on its own only as Takeover and Availability allow (a stopped call to the next agent; a task its best agent can't do, to the next one). A piece task created from an approved split plan is the one exception, and the approval is what allows it. A task started from the interface is a task the owner typed; the page adds flags, never text.

## Project files

- **What it is.** On a project whose folder is a git repository, agents change the project's files without ever touching the folder: Claude's build calls work in a scratch copy, the router runs the project's tests on that copy in a sandbox, the checker judges the change and the test results, and when the check passes the owner lands the change as one commit, which Undo can take back. Built by brief 28; 2.41 folded the older project lines into the sections they belong to.
- **File mode.** A task runs in file mode when it has `--project` and: git is installed; the project's folder is the top level of a git repository with at least one commit, on a branch; the folder is not the router's own folder, inside it or one of its worktrees; Claude's file check has passed on the installed Claude Code version; and the copy fits the limits. Otherwise it runs as before, handoff only, and its card says why. `--project` is taken on `route`, every preset and `split` (see Relay and Split); `vote` never runs in file mode.
- **The copy.** At intake the router records the project's head commit as the task's base and writes the files git tracks at that commit into a new folder outside the project, under the copies root (a setting, so a live check's worktree keeps its own and never reaches a real task's copy; brief 29.1), never in a folder iCloud or another sync manages (29.1's live check: on the synced Desktop, sync moved a folder's modified time beside the file check's copy, and the check counted it as a write; brief 30 makes the check judge files and names only). It never carries `.git`, `.env` or `.env.*`, `.claude/`, `.mcp.json`, `.cursor/`, `.codex/`, `HANDOFF.md` (the handoff rides in the prompt, as before) or a link. The router keeps its own history of the copy outside the copy's folder, where no agent can reach it: a snapshot before every file-mode call. Limits: 5,000 files and 100 MB in the copy; a changed file up to 10 MB; a change up to 500 files. A copy is removed after Land, Discard or Cancel, and when a task is delivered or fails with no change; a task that stopped, or failed with a change, keeps it until then or until it is resumed. A `versus` task in file mode has two copies until the pick, then the picked one's.
- **Who changes it.** Only Claude, and only on build calls: a routed task's doer call; `research-build`'s build stage; `redteam`'s build and revise stages; `collab`'s build stage; a `versus` candidate Claude builds, in its own copy; a split's integration (brief 29); the fix rounds of each. **One exception (D21, brief 29.1):** on `versus`, ChatGPT's candidate is built from a file view, the copy's tracked text files as data in its prompt (binary files and files over 20,000 characters listed only; refused at intake past 100,000 characters), and returns whole files; the redactor and the key scan run on every file it is shown, and a hit refuses `versus` in file mode at intake (file and line, never the value); the router writes its files into that candidate's copy from its reply as it came back, after the path checks and the key scan files in gets, so ChatGPT runs in no folder and holds no file tool. On `versus` in file mode the slots must be Claude and ChatGPT. Those calls run in the copy with file tools that read and write only there and no tool that runs a command. Claude's check and review calls, a split's plan call, and a plan task's plan, revise and fix calls (see The plan), run there read only, and so does the do call of a `--no-files` task (`sr route --project` only): Read, Glob and Grep, no write, no tests, the change always empty, the copy removed at delivery; its doer is always Claude (a label or skill that would pick another is redirected and said), ChatGPT checks. ChatGPT, Grok and Cursor never run in the copy: they get the change as text. A routed task whose doer is another agent changes no file and its card says so; a slot flag that puts another agent in a build slot on a file-mode project is refused at intake. No agent runs a command of any kind. Before every file-mode call the router checks the copy for a path it never carries; finding one, it stops the task.
- **Text-only cards** (brief 33.4). A delivered `--no-files` task on a project with no `SPEC.md` has **Save as SPEC.md** as its card's main action (`sr project save <name> --task <id> --path SPEC.md`, one commit; the draft's entry already has its own, and the saved text leaves out a `## Missing` section, or stays whole and says so when more than the note would go), read from the files record, never from the task's text. Such a card offers no Plan from #n; once the spec is saved its first chip is **Plan the project** (team Plan, "Plan this project from SPEC.md.", no `--from`).
- **Claude's file check.** A probe like Cursor's canaries, kept per Claude Code version in `probe_state.json`, run by the router at intake when a file-mode task meets a version with no pass, and by `sr probe`. One call, a second only if the first errors, from a folder made as a copy is made: it proves Claude can't read, list or write outside the folder (judged from the files and folder names outside it, never a folder's own modified time, and never another task's copy; the probe's own folder sits one level above its copy, so a write one or two folders up is compared; brief 30), can't run a command, loads no MCP server, no plugin but Claude Code's own and no instruction file from above the folder, and can edit inside it. A fail turns file mode off on that version, said in status and on the card; its record keeps the paths that changed outside and Claude's tool calls, names only (brief 30), and `sr probe --json` prints each probe's result whatever the exit, with that record. Until the check has run on the installed version, status and the page read file mode on, since intake runs it before the first file-mode task; they read off when Claude Code gives no version, and for the hour after a check that could not run. Its cost is that one call per Claude Code version; a build call carries WebSearch where today's call has it, so Claude's search checks run before the first one on a new version too (see Web search).
- **Tests.** After each build or fix call (none when the change since the base is empty, and the checker is told so; a call that changed no file keeps the last results; brief 28's issue 16) the router runs the project's test command on a throwaway copy of the copy, so nothing a test writes is kept. The command is set per project from the page (`sr project tests`) and kept in a gitignored list beside the registry, never in the project. It runs as words, never through a shell, in a macOS `sandbox-exec` sandbox the router builds: no network; writes only in the throwaway copy; no reads under the home folder but the throwaway copy and, when its first word starts with `.venv/` or `venv/`, that environment in the project, read only; an environment with no key or `.env` value; a time limit (300 s by default) that kills it. Its output is redacted, cut to its last 20,000 characters, kept in the task's folder and summed up on the call row; the checker and the next fix round see it. With no command set, nothing runs and both are told. The owner picked "the builder runs the tests" (26 Oct); the design chat moved the run to the router the same night, because a model with a shell can read outside any copy. If the sandbox can't be proved on this Mac, tests stay off and status says why. Every file-mode build and fix prompt says whether the project has a test command and, when it has, that the router runs it after the call and the checker sees the results, so the agent never asks for that run, in `### Next` or anywhere else (brief 33's live check: a `### Next` line asked to check a test run the router had already made; brief 33.1).
- **The change.** After each build or fix call the router compares the copy with the base: files added, changed and deleted. The diff, redacted, is kept in the task's folder. A change holding a path the copy never carries, a link or a file over the limit fails that call and stops the task. Checkers, attackers and Claude's reviews get the diff (cut at 60,000 characters, the cut said and the whole file list kept) and the test results as data, with one line telling them to judge the task against them; a failing test is a failure unless the result explains it.
- **Waiting to land.** A file-mode task delivered with a change waits for the owner (`waiting_on: land`) and counts as the project's open task until it is landed or discarded. Its handoff entry is written when it lands, not at delivery: the land commit holds it ending `landed` (`landed (check not passed)` after Land anyway, in place of the task's `failed:` line; brief 30), and nothing is written in the folder after the commit: the card and the log carry the id (the owner, 27 Oct, brief 28's issue 5); a discarded task gets a one-line `discarded` entry; an undone one's entry becomes `undone (<short id>)`. A task with no change is delivered and its entry written as before.
- **Land.** `sr land <task_id>`, and the card's Land button, puts the change into the folder as one commit on the branch the task started from, offered when the task ended passed, fixed or unchecked, and on `versus` when the owner picked it. **Land anyway** (the owner, 27 Oct, D20, reopening D1): after a failed check, `sr land <task_id> --anyway`, on the page a button beside Discard whose confirm lists the check's open musts, lands it with the message and the entry saying the check didn't pass. Nothing lands on its own, and never a blocked or stopped task or a piece. The commit holds the change's paths and `HANDOFF.md` with the new entry, and on a step of the current plan `docs/PLAN.md` with that step ticked (see The plan), and nothing else: no other file in the folder is touched, staged or committed. Refused with nothing written, naming what: a changed text file the redactor or the key scan flags (file and line, never the value); a path of the change with uncommitted edits in the folder, or a new path already there; another branch; a path the branch changed since the base. When the branch moved but none of the change's paths did, the commit goes on top. A router commit interrupted part-way (a land, an undo or files in) leaves the folder as it was or as committed, never half: the router writes a journal beside its log first, and the next land, undo, discard or project command finishes one interrupted after the branch moved; a Turn on undo cut off before its first commit is finished by the next one. Router commits use the project's git name, or a router identity when it has none, run no hooks, and never rewrite history.
- **Undo and Discard.** `sr undo <task_id>` makes one new commit putting every path the land changed back as it was, plus `HANDOFF.md` with the entry marked undone; refused when any of those paths changed since. On a step of a plan, `docs/PLAN.md` is not put back but written again from the plan and its ticks, with that step open, so a later step's tick never refuses an earlier step's Undo (see The plan). One undo per land. `sr discard <task_id>`, or `sr cancel` on a task waiting to land, drops the change: the copy is removed, the one-line `discarded` entry is written, in the entry's own commit, and no other file in the folder changes; refused, with nothing removed, when the task's project isn't in the registry (brief 29.1). A task that stopped or failed with its copy kept is discarded the same way. A split still at its plan or on its pieces is refused (`wrong_state`): its pieces build in that copy, and Reject or `sr cancel` drops it.
- **One writer.** Land, Undo, Discard (a cancel of a task waiting to land included), files in, Save to project, Turn on undo, a write of the project's notes (an edit or a pin) and a plan's tick commit (see The plan) each hold the project's lock (`project-<name>`); another of them on the same project meanwhile is refused at once (`land_refused`, or `project_refused` for the others), with nothing written, naming the task when a land, undo or discard holds the lock.
- **Takeover, resume, fallback.** A Claude build, revise or fix call on a file-mode task that stops is not taken over: the task stops and offers Resume, which puts the copy back to its snapshot from before that call and has Claude make the call again. A plan task's Claude calls stop the same way, read only (see The plan). `sr fallback` is refused for a file-mode task. A `versus` task, as any review preset, is never taken over or resumed. Check, attack and review rounds follow the usual rules.
- **Files in.** `sr project files <name> --file <path> …` copies files into the project's top level as one commit, with `HANDOFF.md` and a one-line entry naming them. Refused with nothing written: a name already there (never overwritten), a `.env` name or a path the copy never carries, a file over 50 MB or a link, a text file the redactor or the key scan flags, a project without git. Allowed while a task is open; that task's Land checks for a clash. The page's drop on a project runs it: the file goes through `/api/drop` with `"for": "project"`, any type (the router checks each file), never renamed; a name already waiting at the drop folder's top level is used as it is when its bytes match, else refused; a drop whose Add is refused moves into the drop folder's `refused/`, so a routed task is never offered it (brief 28's live check). **Save to project** (brief 30, D19): `sr project save <name> --task <n> --path <path>` writes a `done` task's delivered result, without its `## Handoff` and `## Next` sections, as a new `.md` or `.txt` file at a path inside the folder (folders made as needed; no part starting with `.`; never `HANDOFF.md`), one commit with `HANDOFF.md` and the entry `### <date> · saved: <path> (from #<n>)`, refused as files in is and for a task not done or with no text result; on the page, Save to project on a done card.
- **Git for a project.** `sr project new` sets up git when it makes a project (see Project context, Making a project). `sr project git <name>`, the page's Turn on undo, does it for a registered folder without git: the `.gitignore` lines `.env`, `.env.*`, `.venv/`, `venv/`, `__pycache__/`, `node_modules/` and `.DS_Store`, added where missing; `git init`; one first commit of what git then tracks, `HANDOFF.md` included. Its `--dry-run` lists the count and size and runs the key scan, and writes nothing; a hit or the limits refuse.
- **JSON.** Status: `git` (installed, version) and `test_sandbox` (available, why); per project `git`, `branch`, `head`, `tests`, `files_mode` and `why`; Claude's probe gains `files`. A task: `project_files`, since `files` already holds a task's media (state `none`, `waiting`, `landed`, `discarded` or `undone`; `mode`, and `why` when file mode was off; the base and branch; the changed paths with their counts; the diff's file; the latest tests; whether the copy is kept; what was left out; the commit and the undo commit) and each call's `tests`. Log version 17: `tasks.project_files` and `calls.tests`. `land`, `undo`, `discard` and the new `project` verbs take `--json`.
- **The page.** A file-mode card shows the files changed, each diff in the side panel, and the tests line. A change waiting to land shows Land and Discard on the card and in Needs you, each behind the page's confirm (the second click names the command); a failed one shows Land anyway beside Discard, its confirm listing the open musts, and Needs you lists it as "Land anyway?"; a `versus` task on a project shows each candidate's files (its first 12 and how many more) and tests, with its `## Handoff` section folded under its text as "Its handoff"; a landed one reads "Landed · <id> · Undo". A project shows its test command with Set or Change, Turn on undo when it has no git, and takes dropped files into a sheet with Add. The Settings tab's Setup section has a Git row. A card lists the first 12 changed files and how many more; a split at its plan or on its pieces shows its copy building, with no button, and each piece's part on the split's card is its first 6 files and how many more; the side panel lists more than 8 in a select. The page starts one run per task at a time: a second click while one runs does nothing. `/api/runs` gives each run on a task its `on` (its action and task id, never its text; none for a run on no task), so a reloaded page shows a run still going. The page never runs git and never writes in a project; the router does every write.
- **Not in this section yet.** Any agent but Claude changing files, beyond the router writing ChatGPT's `versus` candidate and a plan's `docs/PLAN.md` (see The plan); any agent running a command; a `versus` piece on a project split; merging when the branch changed the same files; editing or deleting a project's files on the page (its notes in `HANDOFF.md` aside, see Project context); anything Test, Run and Secrets don't do (brief 31, their own section); the router changing its own folder.

## Test, Run and Secrets

- **Why.** The owner's goal is never to open Terminal (the never-Terminal plan). A project's tests, its own program and its keys were the last things the owner still ran or edited there. Brief 31 puts each behind a button, and keeps every one of them theirs: the router never starts a program, and a key's value is never shown.
- **Test.** `sr project test <name>`, the page's Test, runs the project's test command exactly as the router runs it after a build (see Project files, Tests): a throwaway copy of the project's committed files at its head, the sandbox, no network, no key, the 300-second limit, the output redacted with the router's `.env` values and the project's. No task, no agent, no log row; the newest 10 results are kept under `run/projects/<name>/tests/`, and `sr project test <name> --status` shows a running Test's output so far (whole lines, redacted), else the last one's. It exits 0 when a Test ran, whatever its outcome. Refused for a project with no test command, no git or no commit, for the router's own folder, and while a Test is running on it. It never touches the folder.
- **Run.** `sr project run-command <name> -- <words>` keeps a project's run command beside its test command, in `config/project_runs.json` (gitignored), split as a shell would split it and never run through one. `sr project run <name>`, the page's Run after a confirm naming the command, the folder and the `.env` names it passes, starts it in the project's real folder, unsandboxed, with no time limit, in its own session, so closing the page or Terminal doesn't end it. Its environment is the router's own with every name in the router's `.env` and every billing switch removed, and the project's `.env` laid on top. A supervisor redacts every line (the router's `.env` values and the project's) before it is written to `run/projects/<name>/`, keeps the newest 5 MB, and records the exit. One run per project. `sr project stop <name>`, after a confirm, sends the run's group SIGTERM, then SIGKILL after 10 seconds; a run is known by its process id and start time together. Refused: no run command; the router's own folder; a `.env` that is a link or not a plain file, or, on a project with git, one git tracks or doesn't ignore; a run already going; a `.env` name holding an entry of `never_run_env`, matched without case (see Money).
- **Only the owner starts a run.** Nothing else ever does: not the router on its own, an agent, a task, Auto, a schedule or a resume. A run that ended is never restarted.
- **What the page shows.** A Test's or a run's output in the side panel is a display copy made by `--status`: terminal escape sequences taken out, any other control character shown as a mark, and the whole redacted again (taking characters out could join a value printed in two parts); the kept files stay as written. The panel updates in place every 2 seconds and follows the newest line only while you are at the end. Run's confirm shows the command, the folder and the `.env` names in their own blocks. The Secrets list scrolls in its own box; the secret's live command line is composed by the page, naming the secret and never its value, while the command that runs is the builder's.
- **Secrets.** `sr project secrets <name>` lists the names in a project's `.env`, each set or empty, never a value. `--set <NAME>` takes the value on stdin, never as an argument; `--remove <NAME>` takes a name out. The file is written whole, mode 600, every other line kept byte for byte, so `dotenv_values` reads back exactly what was sent, and a value it can't read back (one holding `${…}`, which python-dotenv expands inside any quotes) is refused. An empty value is kept empty; a name written twice keeps its first place. Refused: a name that isn't upper case letters, digits and `_`; a `.env` that is a link or not a plain file; on a project with git, a `.env` git tracks or doesn't ignore, checked before a `.env` is made too; the router's own folder, whose `.env` is never written from the page; a value with a second line, a NUL, or more than 4,096 characters. On the page: the names, Add, Change and Remove, a password field that clears after Save; the live command line says the value went on stdin and never shows it.
- `sr status --json` and `sr project list --json` give each project its run command, its run's state, its last Test, whether a Test is running, and how many secrets it has. Built by brief 31.

## Next steps

- **Why.** The owner's ask (28 Oct): the router should suggest the next move, as the design chat does, not only report what it did ("after a research phase, it suggests getting to work on building"). Brief 33 (the never-Terminal plan's D27, D28 and D30) adds chips, Build from this, What now? and a project's Ideas list. None of them runs anything on its own: a chip fills the composer, and the owner sends.
- **Chips.** The page shows up to three chips under the newest card of a project's or a chat's view, when that task was delivered and nothing newer is in the view except tasks that were cancelled, discarded or undone. Delivered means `status` `done` with an `outcome`: a change waiting to land isn't yet, and a discarded or undone change gets no chips. An older card keeps its chips in its Details, under "Suggested next". There are none in Quick tasks, All tasks or History, on a piece, or on a card that failed, stopped, was blocked or cancelled. Chips come from two sources, with no extra call. First come the router's own moves, chosen by code from the task's row and state, never by a model: since brief 33, **Build from this** on a delivered result with text, except a `quick_answer`, `recall` or `make_media` task or a forgotten one; since brief 33.1, the plan's moves, **Plan from this** and **Build step k**, which fill their own team and pills (see The plan). Then come the agent's own, read from the delivered result on its call row: on a project task, the `### Next` lines of its `## Handoff` section; on any other task, its `## Next` section; both read by the same rules. A chip whose words match an earlier one's is dropped. A click fills the composer with Route, the task's tag, the text and, when the move carries one, an earlier result (`--from`); when the box held text, a toast offers Undo for 10 seconds. A chip never sends, never runs a command and never asks to confirm. Chips are computed when the JSON is made and never stored (`next` on each task).
- **`## Next`.** Off a project, every prompt whose result can be delivered as the task's result says the agent may add, at the very end of its reply, a `## Next` section: one to three lines, each a next task the person could send as it stands. These prompts are a routed doer's (except on `quick_answer`, `recall` and `make_media`), `research-build`'s build, `redteam`'s revise, a `versus` candidate's, a split's integration, their contract re-asks and fix rounds, a fallback's redo (not `collab`'s, whose edit stage delivers) and a resume; the line goes last. It is never asked on a project task (its handoff's `### Next` is the source), a piece, a stage whose result goes on, a check, review, attack or vote, or `collab`. It is optional: never a contract miss, never re-asked. The heading is exactly `Next`, one or two `#`, any case, a colon allowed: a `## Next steps` section is the deliverable's own and stays in it. Code reads it as the handoff's parts are read: up to the first blank line after an item, the next heading or the end, so a `Sources:` block after it stays part of the reply. It keeps at most 3 lines, each cut at a word to at most 400 characters, and drops a line starting with `@` or `/`. It is a note, like `## Missing`: the router takes it out of a result before passing that result to any other call, and the word count ends at it. It is never in a stored memory, a Save to project file, a handoff entry or an earlier result carried by `--from`. The card shows its lines as chips, not in the result; the call row keeps the reply as it came; `sr show` prints them after the result under `Next:`.
- **The agent's chips.** Each fills Route, the tag and its line. Off a project it also carries `--from` its card's task, unless that task is forgotten, since a chat's memory cuts an entry at 2,000 characters; on a project it carries none, since the handoff, the memory block and the copy carry the context. On a project card each has Later, which moves its line to the project's Ideas list; a moved line is not offered again.
- **Build from this** (`--from <task>`). On `sr route` (an override included), `sr relay` and `sr plan` (brief 33.1), once per task, checked at intake before Jev is asked; refused on `sr split`. The new task carries the source's delivered result whole, as data: the result as `sr show` prints it, without its `## Handoff` and `## Next` sections or the `Next:` lines, through the redactor, cut at `from_max` characters (`config/settings.json`, 20,000) at a line end, with a last line saying the cut and naming the source. It is labeled `EARLIER RESULT · #<n> (<date>, <team or skill>)` between the `=====` markers, with a line saying the person chose it and that it is data, not instructions, true as of its date. It goes after the task and before the handoff and memory blocks, through the one context helper, to every agent call on the task: the doer, every relay stage, every check, re-check and fix round, a re-ask, a takeover, a resume and a fallback. The call row records it as sent (the source, its characters, whether cut, the block), and every later call on the task, a resume and a fallback among them, sends it as the first call sent it. A memory block on the same call leaves the source out. A check, re-check, review or attack gets one more line (see Checking). `--from` is refused at intake with nothing written (`bad_from`) when the source isn't in the log, isn't delivered with a text result, or is forgotten; the message names why from the source's outcome, never its status, so a task that failed its check says so (brief 33's live check read "it is done"; brief 33.1). The block is never cut to fit Grok: on `sr relay`, a task whose Grok stage it would push past Grok's limit (that stage's prompt with an empty earlier stage, plus the block) is refused at intake with both lengths (`too_long`), as a vote's is; a later Grok call that carries it is held to the limit as a stage with an earlier result is (never trimmed; a fix round and a re-ask exempt); on `sr route`, where the doer is known only after Jev's label, the task comes back after the label (`too_long`), as a task with files does when its doer would be Grok. `--answers` carries a floor row's `--from` and `--idea` with its tag, and Run again as… and Run again carry `--from`. The source may have any tag, and the new task keeps its own. It makes no thread. The page shows a From pill in the composer and "Built from #<n>" on the card.
- **What now?** One line in a project's pinned head, with one move and its control, chosen by code and never stored (`what_now`); the first match wins. The plan's rungs (brief 33.1) go between the third and the fourth (see The plan); chats have none. A suggest is no task for What now?, running or ended.
  - a task of the project waiting on the owner: "Waiting on you", with Open (a plan with questions: "Waiting on you: #<n> · answer <k> questions");
  - one open and not waiting on them: "#<n> is running", with no control;
  - the newest top-level task that wasn't cancelled, discarded or undone ended without delivery (failed its check, blocked or stopped): its outcome, with Open;
  - that task was delivered and has chips: "Next: …", with the first agent chip, else Build from this;
  - else "Send a task to start." or "Nothing suggested", with the Ideas button when there are ideas.
- **The Ideas list.** Each registered project has one, kept by its name in the log (table `ideas`, log version 18), never in the project folder, in memory or in a prompt: an idea reaches an agent only as a task the owner sends from it, or in the list a suggest reads so it repeats none. It holds one-line ideas of at most 400 characters, each with its source (Later on #<n>, or added) and its date, with at most `ideas_max` open (`config/settings.json`, 50; past it, `ideas_full`). Ideas are added by Later, by Add on the list or by Suggest ideas. Text that is empty, runs to a second line, passes 400 characters, starts with `@` or `/`, or is matched by the key scan or a `.env` value is refused (`bad_idea`), and one already open is not added twice. Send fills the composer like a chip, with an Idea pill. A task sent with it carries `--idea <id>`, checked at intake before Jev is asked; it is refused (`bad_idea`) for an idea that isn't open, belongs to another project, or is on a task without that `--project`, and on a split. While that task is open the idea reads "sent as #<n>"; it is used when the task is delivered (a change once it lands), and open again if the task ends any other way. Dismiss asks once and takes it off the list; the log keeps it. A used idea leaves the list for a folded "Used (n)" list under it, each with "used by #n" (brief 33.2's fix). `sr ideas <project>` lists them; `--add [--source <task>] -- <text>` and `--dismiss <id>` change them; each takes `--json`. Add to plan (brief 33.2) on an open idea's row fills the composer with Plan, the project, the Idea pill and the text (see The plan). **Suggest ideas** (brief 33.4): `sr ideas <project> --suggest`, the Ideas sheet's button. Each click is one task, `mode: suggest`: one Claude call with no tools, no Jev, never checked, no entry, nothing retained, no card in the stream; it shows in History and `sr log`. It reads the project's usual blocks, `docs/PLAN.md`, the file list and the ideas already there (`suggest_ideas_chars`, 6,000). Up to 3 lines become open ideas, read "Suggested by #n"; a bad line is dropped and counted, its text never shown; none usable fails, with no re-ask. Refused while Claude is unavailable, past `ideas_max − 3` open, or with one already running on the project.
- **Records.** Log version 18: `tasks.from_task`, `tasks.idea` and the table `ideas`; an idea's state is derived from its row and the task that carries it, never stored. JSON: `next`, `from` (task id, number, characters, cut) and `idea` (id, text, state) on a task, and `from_given` (the block as first sent) on `sr show --json`; `what_now` on `sr log --json --project` and per project in `sr project list --json`, beside the project's open idea count (`ideas`), which status carries too; every `sr ideas` action's envelope adds `ideas` (the list as it stands) and `dismissed` (a count) after its eight keys. Reason codes `bad_from`, `bad_idea`, `ideas_full`, and `too_long` as a return. Built by brief 33.

## The plan

- **Why.** The owner's picks (the never-Terminal plan's D10, D14, D27, D28 and D30): on a project, a plan made from the project's own files and attacked before the owner sees it, which says up front what it needs from them, holds each step to a finish line a test can show, and keeps a `docs/PLAN.md` that always shows what is done. Brief 33.1 builds it by hand: every model call and every land is their click. Brief 34 (Auto) clears those stops inside a plan the owner approved; brief 33.2 adds the spec, Revise plan and Add to plan; brief 33.4 adds starting from an idea, questions first and Suggest ideas.
- **Plan is a team, on a project only.** `sr plan --project <name> [--from <task>] -- <text>`, where the text says what to plan: a goal, a focus, or "Plan the first version." A plan task (`mode` `plan`) runs `redteam`'s chain as it is filled now: Claude plans (stage 1), ChatGPT attacks (stage 2), Cursor attacks (stage 3, optional as on `redteam`), Claude revises (stage 4), and ChatGPT checks. Jev is not called. It is refused at intake with nothing written (`plan_refused`, naming why): a slot flag, `--chat`, a file, `--web` or an override; a project without file mode, with file mode's why ("Turn on undo first" for a folder without git); a step of the current plan whose failed change is still kept (Land anyway or Discard it first). With no current plan, or one whose steps are all done, it makes a new plan; with a current plan that has an open step, a revision (see Revise plan). The plan task is the project's open task from intake until it lands, is discarded or ends any other way.
- **What the planner reads** (pick 6). Claude's plan, revise and fix calls run read only in a copy of the project, as a split's plan call does, and carry: the handoff (the notes included) and the memory block; `## All agents`, `## Claude` and `## Planner`; the project's teams menu, built as a project split's but without `vote` (route, `research-build`, `redteam` and `collab`); the project's test command, or that it has none, and its last Test's outcome (passed, failed, timed out or never run, with its date); and, with `--from`, the earlier result. Every call on the task also gets the copy's file list as data: paths and sizes, at most 500 with the cut said, through the redactor, a path the key scan matches left out and counted. The attackers and the checker never see a file; the list tells them what exists.
- **Its shape** (the contract, checked in code, with one re-ask). Stage 1 returns exactly one of three answers: a plan, One step or, on a new plan, Questions (see Questions first). **A plan:** `## Steps`, 1 to 12 numbered steps, each a task under 400 characters, not starting with `@` or `/`, that the router could run as it stands, followed by three lines: `team:` (on the menu), `why:` (under 200 characters) and `done when:` (under 300 characters); then `## Needs from you`, with lines `key: <NAME> (step <k>): <what for>`, `account: <what> (step <k>)`, `decision: <question> (step <k>)` and at most one `test command: <words>`, or `none`. A plan misses the contract when a step's team isn't on the menu, a key's name isn't upper case letters, digits and `_`, or starts with a digit (the names `sr project secrets` takes), a need names a step past the last, or a line breaks the counts above. Each of a step's three lines is one line: several tests go on the one `done when:` line, separated by semicolons. A line after them misses the contract, named as such, and never becomes part of the step's task; a `key:`, `account:` or `decision:` line that misses its form is told the form. Every prompt that asks for the plan back (stage 4, the fix round and their re-asks) says the shape whole. **One step:** `## One step`, with one line saying why, a `task:` line (under 400 characters) and a `team:` line (on the menu). Stage 4 and the fix round return the plan in the same shape, with `## Answered`; one step is no longer allowed there. Every plan result passes the contract in code before it goes on. A plan task's calls return no `## Handoff` section and get no `## Next` line.
- **Finish lines are tests** (pick 4, idea F). The planner prompt says: each step's done-when is something a check can confirm from that step's result; a step that changes code finishes when a named test passes (the test, its file and what it checks), so the router's test run after the build shows it; and on a project whose last Test didn't pass, or that has no test command, step 1 is the smallest skeleton that runs, with one test that passes, and the needs propose a test command when none is set. The attack prompt on a plan names the same things to look for. The check gets both attack lists, the file list, the last Test's outcome and the plan's check line, which fails the plan (a must) for a code step whose done-when names no test, a step 1 that breaks the skeleton rule, a key or account a step needs that the needs don't list, or a step that can't work as written or in that order; a choice the plan puts to the owner stays a note (see Checking).
- **One step** (idea C). A `## One step` answer ends the plan task as a split's `## No split` does: status `failed`, reason `one step: <line>`, nothing attacked, the copy removed, no entry. Its grey card offers **Build it**, which fills the composer with that task, its team and the project. What now? shows it as "One step: <task>", with Build it, not as a failure.
- **Questions first** (brief 33.4). On a new plan (never a revision), stage 1 may return `## Questions` in place of `## Steps`, only when an answer would change the steps: 1 to 3 questions, each under 300 characters, with 2 to 4 options `A.` to `D.` under 120 and `guess: <letter>` naming one of them; anything else is a contract miss, with one re-ask. One round, in code: the call carrying the answers may not return `## Questions`. Nothing is attacked or checked while it waits. The owner answers on one card, a chip or an Other line per question, the guess marked and never pre-picked, or taps Use your best guess; `sr plan --answer <task> [--pick <k>=<letter>]… [--other <k>=<text>]… | --best-guess`. Other is checked as an idea's text, refused by name, never quoted. Every later call on the task gets the questions and answers as one labelled data block. At Approve, in the land commit, `docs/PLAN.md` gets them under "Decided before planning" and the notes' one section "Current plan's decisions" is replaced; a new plan with no questions clears it, a revision keeps it, its Undo puts it back from a copy on the plan's record, and Reject, discard or a failure writes nothing.
- **No takeover.** The plan's Claude calls need the files, so they are never taken over: a stop ends the task and offers Resume by Claude in the same copy, as a file-mode build call's stop does. A plan has no fallback. Attack and check rounds follow the usual rules.
- **Approval.** When the check ends (passed, fixed, unchecked, or failed twice), the router writes `docs/PLAN.md` into the task's copy from the plan, and the task waits as any file-mode change does: **Approve** is Land (`sr land`), **Reject** is Discard, and after a failed check **Approve anyway** is Land anyway, its confirm listing the open musts. On a new plan, when the notes' "Current plan's decisions" differs from what the router last wrote there (its last land's, or the copy its last Undo put back), Approve's confirm says it will be replaced. Before that, the owner may change a step's text, team or done-when, move it up or down, or drop it (`sr plan --edit <task> --step <k> …`, one change per command). Each edit passes the contract's rules in code, renumbers the needs' step references (a need whose step was dropped is kept with no step), renders `docs/PLAN.md` in the copy again, and is logged beside the planner's version (`edited`). The land commits `docs/PLAN.md` and `HANDOFF.md` with the router's entry (Produced `docs/PLAN.md (<m> steps)`, Status `plan #<n> approved`, Next step 1's text, and "No tests ran: a plan changes no code; each step's tests run after its build"), and the plan is stored in memory as any delivered result is. A `docs` or `docs/PLAN.md` in the folder that is a link refuses the land (`land_refused`), naming it: the router never writes through a link. A plan is never edited after it lands; it changes only by its ticks.
- **The current plan** is the project's newest plan task that landed and wasn't undone. An Undo of the plan's own land is the usual Undo, refused once a step has ticked (`docs/PLAN.md` changed since); undone, the plan is no longer current.
- **Revise plan** (brief 33.2). A plan task on a project whose current plan has open steps is a revision: its record carries `revises` (the old plan) and `inherited` (d, the done steps before the first open one), and the done steps are copied byte for byte from the old record, their covers matched to the current spec by the example's text ("example changed" where it is gone). The planner returns only the steps after the done ones, numbered from d+1 (d + new ≤ 12), with `## Needs from you`, `covers:` and `## Changed` (one line per open step it changed or dropped, or `none`); `## One step` is not allowed. Every call gets the current plan as `PLAN SO FAR`. Ticks follow `revises` back. The land renders `docs/PLAN.md` titled "Plan #m (revises #n)", the inherited steps ticked with their tasks; the old plan is no longer current and its Undo is refused; the revision's Undo makes it current again. Edits before approval touch new steps only; Stop here marks start empty; calls and the estimate count the new steps. The page: Plan again in the plan panel; the revision's board with the inherited steps greyed.
- **Add to plan** (brief 33.2). `sr plan --idea <id>`, checked as route's `--idea` (`bad_idea`): with a current plan that has open steps a revision, whose planner keeps the open steps unless the idea needs a change and names any change in `## Changed`; else a new plan from the idea. The idea's states derive as any task's. A One step answer's Build it carries the idea.
- **Build step k** (pick 4). On a project whose current plan has an open step, the chip **Build step <k>: <text>** fills the composer with the step's text, its team (Route or a preset), the project and a Step pill: `--step <plan task>:<k>`, on `sr route` or `sr relay`. It is refused at intake (`bad_step`): a step that isn't the current plan's first open step; a plan that is no longer current; a project without file mode, with file mode's why, so a step never ticks without its work. The owner may change the team or the text before sending; the task is still that step, held to its finish line. Sent, it runs as a task of its team, exactly as typed would, and its row records the plan and the step. Steps run one at a time, as every project task does.
- **The finish line is checked.** Every call on a step task gets a STEP block: "This task is step <k> of the project's plan (docs/PLAN.md, plan #<n>). Its finish line: <done-when>. docs/PLAN.md is the router's: don't change it." Its check and re-check get one line: the finish line is a must; in file mode it is judged from the change and the test results; a finish line that names a test is met only when that test is in the project after the change, tests what the step says, and shows as passing in the test results. If a build changes `docs/PLAN.md` in the copy, the router puts it back before the check, to the file as it stood when the task started (a run step's own start snapshot), and the card says so.
- **Ticks, by code.** A step is done when its step task landed and wasn't undone, or was delivered with no change; this is derived from the rows, never stored, and a step that failed, stopped, was blocked, cancelled or discarded stays open. A land's commit also holds `docs/PLAN.md`, with that step ticked and its task named; a delivery with no change (a research step, say) gets its own commit, `docs/PLAN.md` alone, under the project's lock. Undo writes `docs/PLAN.md` again from the plan and its ticks, with that step open, as it rewrites the `HANDOFF.md` entry, rather than putting the file back, so an earlier step can still be undone after a later tick when its own paths are unchanged. When `docs/PLAN.md` isn't what the router last wrote: with uncommitted edits in the folder it is left out of the commit, said on the card and in What now?, and the tick still counts; changed by a commit outside the router, it is written over in the same commit (git keeps the other), said on the card; a link is left out and said, as on a land.
- **`docs/PLAN.md`** is written only by the router, from the current plan and its ticks: a title; a line saying the router writes it; the plan's number and date, and "<d> of <m> steps done"; the steps as a checklist, each with its team, done-when and why, and, when done, the task that did it; the needs; and "Decided before planning", the current plan's questions and answers (a revision carries its old plan's).
- **Needs up front** (idea D). Code tracks two kinds of need: a key (set or not, from `sr project secrets`) and the test command (set or not). Accounts and decisions show on the plan card and in `docs/PLAN.md`, and are never tracked. For the next step, What now? shows "Before step <k>: set <NAME>" for a key it needs that isn't set, with the Secrets button naming it, or "Before step <k>: set the test command" while the plan proposes one and none is set, with Set (the proposed words filled in, and a confirm naming them). An unmet need never refuses anything: the owner may send the step anyway.
- **What now? and the router's moves.** The plan's rungs go between Next steps' third rung and its fourth: first "SPEC.md changed since plan #n · Revise plan" (`spec_changed`) while the plan has an open step and the folder's `SPEC.md` hashes differently from the one the plan read (deleted or added counts); a plan waiting for approval says it on its card and in Approve's confirm, which re-reads the plan first; nothing is refused; (a) the next step's unmet key or test command; Build step <k> is offered, as a chip or a move, only while the step's needs are met; (b) "Build step <k>: <text>", with its chip; (c) **the finish line** (idea G): when every step of the current plan is done, "All <m> steps done", with up to three chips: when `SPEC.md` has a `## Done when` list, **Check against the spec** first (Route, the project, "Check the project against SPEC.md's `## Done when` list: for each item, D1 on, say met or not met, with the evidence (the test or the file), then what is missing. Change no files; report only."), **Write the README** and **What next**, Set the run command staying in Project tools; without the list **Write the README** (Route, the project, "Write README.md for this project: what it does, how to set it up, how to run it and how to test it."; on either list it reads **Update the README** once the project has a `README.md`), **Set the run command** (it opens that setting, shown only when none is set) and **What next** (Plan, the project, "Plan what to build next."), shown until a top-level task newer than the last step's exists. A plan waiting on approval is the first rung; a One step end is the third, as One step says. The router's moves gain **Plan from this** (Plan, `--from` the task, "Plan this project from #<n>."), first, on a delivered result with text on a project with no current plan or one whose steps are all done, with Build from this's exceptions; on a project whose current plan has an open step, **Build step k** comes first and Build from this is not offered; and a plan task that landed offers Build step 1.
- **Records and JSON.** Log version 19: `tasks.plan` (a plan task's plan as the planner returned it, the owner's edits, and the hash of the `docs/PLAN.md` it rendered) and `tasks.plan_step` (a step task's plan task and step). Reason codes `plan_refused` and `bad_step`. JSON: on a plan task, `plan` (its steps, each with its state and task; its needs, each key and the test command set or not; and the estimate); on a step task, `plan_step`; per project, `plan` (the current plan's number, steps done and total, the next step, and the newest step's note when `docs/PLAN.md` was left out or written over); in status, `plan` as `split` has it (`ready`, `why`, `description`, `chain`, `calls`, `max_calls`, `project`); on a One step end, `one_step` (why, task, team); on `sr show --json` of a plan task, `plan_menu` (its menu as it stands now); and `what_now` with the rungs above. Built by brief 33.1. Brief 33.4, no log bump: the plan record gains `questions`, `answers`, `decided`, `section_before` and `section_written`; call kind `questions`; `mode: suggest`; `waiting_on: answers`; settings `idea_max` and `suggest_ideas_chars`; reason codes `bad_answers` and `suggest_refused`; a task's JSON gains `questions`, `text_only` and `save_spec`, a plan's `decided` and `section_edited`, `sr ideas --json` `suggest`, and status `limits`.

## Models

- **Why.** The owner, 29 Oct (D33): "i want to be able to call any model through the router … different skills and teams use different models by default." Brief 33.3 builds it. Until then every Claude call ran `--model sonnet`, and ChatGPT and Cursor ran their pins.
- **Which model a call uses.** The router picks the agent as before (the skill table, a preset's slots, Takeover and Resume), then that agent's model, the first of these that applies: the task's own choice for that agent (`--model <agent>=<model>`); the default for the call's stage or role (a preset's stage, or a role such as plan, build, revise, fix, check, attack, review, integrate or vote); the default for a build in a copy (`file.<role>`: a relay's or split's stage in file mode, and a routed build's do and fix calls there, except a `quick_answer`, `recall`, `web_research`, `x_social_pulse`, `meta_social_trends` or `make_media` doer, which keeps its skill's); the default for a routed task's skill (its doer's do and fix calls); the agent's default. A model never changes which agent makes a call, how many calls a task makes, or who checks: a check is still never made by the doer's agent.
- **The defaults** (the owner's OK, 29 Oct), pinned by full id, never by alias, since Claude Code moves an alias when it updates itself. Claude's agent default: Sonnet 5.5. Code builds: Opus 5.5, for a routed `code` task's do and fix calls and, on a file-mode task (a plan's steps included), Claude's build, revise, execute, fix and integration calls; nothing else on a project, so a routed `recall` or `web_research` doer there keeps Sonnet, and a stage default beats a skill default. Plan's planning calls (stage 1, stage 4 and the fix): Fable 5.1 while Fable is on, else Opus 5.5, and the card says why. `quick_answer` (nothing checks it, so not Haiku), Claude's checks, reviews and attacks, and every other Claude call: Sonnet 5.5. ChatGPT `gpt-6.1-sol` and Cursor `grok-4.7-high`, their pins in `config/agents.json`. Grok Bot and Jev have no model choice. Each id and alias is confirmed from the installed Claude Code's and Codex's own help, never from memory.
- **Where they live.** A tracked file holds the public defaults: each agent's allowlist, Claude's default (Sonnet 5.5) and the time limits, with no per-skill or per-stage default, so a clone on another plan runs Sonnet everywhere; only the owner edits it. Their own defaults per skill and per stage, and the Fable switch, live in a gitignored local file the router writes only through `sr models` (Settings → Models), as `sr notes save` writes the router notes; they are seeded with `sr models set …` at the switch-over. `config/agents.json`'s pins stay the owner's to change. `sr models --json` prints the defaults in effect, each with its layer and file. `sr models set` refuses a skill's default for an agent the router itself can never send that skill's do or fix calls to: any agent on a skill that is Grok Bot's alone or isn't routed, and Cursor on every skill. One already in the file stays until it is cleared, is named on its row, and is read only by a task that names the agent or by `--no-files`.
- **Per task.** `--model <agent>=<model>` and `--effort <agent>=<level>` (Claude's `--effort`; Codex's `model_reasoning_effort`), each agent at most once, on `route` (any agent, for whatever calls it ends up making), `relay` (only an agent the preset's slots hold), `split` (only its plan and integration calls; the pieces use their teams' defaults), `plan` and a step. It is checked at intake, before Jev is asked and before any probe runs, and refused with nothing written (`bad_model`, naming why) when the agent can't make a call on the task, the model isn't on its allowlist, or it is Fable while Fable is off, or the effort isn't one the agent takes. Every call that agent makes on the task uses it, a resume and a fallback's redo included; a takeover's substitute uses its own defaults, and the takeover line says so. Run again as… and a chip don't carry it.
- **Allowlists,** in the tracked file. Claude: the full ids of Haiku 5.5, Sonnet 5.5, Opus 5.5 and Fable 5.1, with `haiku`, `sonnet`, `opus` and `fable` accepted as input and stored as the full id they name. ChatGPT: the Codex models the ChatGPT plan includes, each listed with its source. Cursor: pinned Grok models only (see Cursor). A name off its agent's list is refused everywhere, and a local layer naming one is ignored, with why in status.
- **No usage credits** (see Money). Claude Code's `-p` mode charges usage credits without asking, and on the Max plan Fable is free only up to half the weekly limit (Claude Code's model page and Claude's plan page, read 29 Oct). The router can't see whether usage credits are on for the account; only the owner can. So Fable is off in the router until the owner turns it on in Setup, and turning it on is their confirmation that usage credits are off on their account; the switch's words say so. While it is off, a Fable default falls back to Opus, and the card says so; a typed Fable is refused (`bad_model`). A cost figure in a stream on a plan login is an estimate, never a charge. Only where a tool's stream carries a field marking a call billed to usage credits does the router act: the call's task stops (`credits`), Fable turns off, and status and the card say so; nothing is retried. Claude Code's stream carries one (the rate-limit event's `isUsingOverage`), so a Claude call billed to usage credits stops its task (`credits`), turns Fable off and says so, nothing retried; Codex's stream carries none, so for ChatGPT the account's balance is the guard. The owner's Fable switch stays the first guard; this stop is a backstop after a billed call.

A served model that differs (Fable's safety fallback re-runs a flagged cybersecurity or biology request on Opus) shows as the card's one-line note and is never a failure. ## Auto

- **Why.** The owner's D14 and D15 (26 Oct), D28 and D31: one Auto switch per project that runs an approved plan's steps without a click per step. Plan approval, landing the finished run and Run stay theirs. Brief 34 builds it.
- **The run.** `sr auto <project> --on`, the project's Auto switch, starts a run on the current plan from its first open step. Refused with nothing written (`auto_refused`, naming the first that holds, in this order): a task of the project open other than its own stopped run; the project's run running, or finished and waiting to land; its run stopped on a step that failed twice or was blocked (Land the run so far or Discard run first, then build it by hand); no current plan or no open step; the next step's key or test command not set (Auto never starts a step with an unmet need); file mode off; Claude unavailable. The run, stopped or not, is the project's open task until it lands, is discarded or ends: one run per project, no other task on the project meanwhile, and Undo of the plan's own land refused. A stopped run waits on the owner (`waiting_on: auto`), a finished one to land (`waiting_on: land`); on either, `sr cancel` is Discard run. `sr auto <project> --off` stops a running run after the step in progress, never mid-call.
- **One copy, like a project split.** The router makes one copy from the project's head, owned by the run, and snapshots it as each step starts. Each step runs as a task of its team as Build step k sends it (its text, team, `--step`, STEP block and finish line, the same prompts byte for byte, and its models as Build step k's), one at a time, in the run's copy. At a run step's intake the open-task rule is set aside, since the run holds it, as a split holds it for its pieces, and a step the run passed counts as done for the next step's `--step`. Its checker judges its part from its snapshot against its finish line, and the tests run after each build and fix. A step never lands on its own: `sr land`, `sr undo` and `sr discard` refuse a step of a run (`wrong_state`). Nothing is committed in the folder mid-run: a step's tick is written in the copy's `docs/PLAN.md`, a step with no change included; a step's build that changes `docs/PLAN.md` has it put back to the file as it stood when the step started, never the run's base, which predates the ticks. Steps get the handoff and memory like any task of the project and return their handoff sections, but write no entry; when the run lands it writes one entry built from them (each step's Produced line, the last step's Status and Next) and stores each step's memory. A discarded run stores none.
- **What Auto clears** (D14's friction stops): starting each next step; a passed or fixed step going into the run; and one retry of a step that failed its check twice: that attempt ends `failed`, the copy goes back to the step's starting snapshot, and the step is sent once more as a new task of the run (a file-mode task has no fallback).
- **Where it stops**, each waiting in Needs you: before a step marked stop-here; at the budget; when a step fails again after its retry, is blocked, is delivered unchecked, or stops; before a next step with an unmet need; on `sr cancel` of a running run or its step (a stop that keeps the copy, never `cancelled`; the page offers no Cancel on a run or a run's step: the switch is its one Stop), or the switch turned off; on the copy's limits, a refused intake, Claude unavailable, a `credits` stop or an unexpected error (the reason its type only, the copy kept); before a step or a retry when the folder's `SPEC.md` hashes differently from the run's recorded one (`spec_changed`, "Auto stopped: SPEC.md changed since the run started"; on again takes the new hash, its confirm saying the remaining steps will use the new SPEC.md); at the plan's end, where the run waits to land. A stopped run keeps its copy. `--on` goes on from where it stopped: a stopped step is resumed as Resume allows, in the same copy; a step that ended since is read as it stands; one Resume can't take is started again from its attempt's snapshot, its row cancelled; a run stopped on its last step is finished; else the step it stopped before is started. It is refused while the cause remains.
- **Stop here.** Any step of the current plan may be marked or unmarked, before or during a run (`sr plan --stop-here`). The mark is kept in the log, never in `docs/PLAN.md`, so marking commits nothing. A run stops before starting a marked step. A mark is passed when an `--on` starts or goes on at that step, whatever stopped the run before it, and stays passed for that run.
- **The budget** (D15): `ceil(1.5 × U)`, U being the plan card's upper call estimate for the steps the run covers, Jev's labels apart. Every model call row of the run's step tasks counts (Claude, ChatGPT, Cursor or Grok; retries and takeovers included; never Jev's label): calls, never tokens, read live from the rows. It is checked before each step and each retry; once reached, the run stops (`budget`), with the calls used and the budget. A step already started finishes, so a run can pass its budget by up to one step's calls, and the switch's confirm says so. `--on` after a budget stop gives `used + ceil(1.5 × U_left)`, U_left being the steps left's upper estimate. `SR_AUTO_BUDGET=<n>`, read at every `--on`, sets the budget, on a scratch log only.
- **The run lands as one.** At the plan's end the router writes `docs/PLAN.md` in the copy with the run's steps ticked, each naming its task, and the run waits to land. **Land run** commits the whole change (its paths, `docs/PLAN.md`, and `HANDOFF.md` with the run's one entry: the steps' sections and the steps' test runs, each step judged by its last run), as Land does and with Land's refusals; the commit's message names the steps that landed and the plan's total (`sr: Auto: plan #<n>, steps <a> to <b> of <m>`). **Discard run** drops the copy and writes one `discarded` entry, its own commit. **Undo** takes the whole run back and writes `docs/PLAN.md` with those steps open. A stopped run may be landed as it stands ("Land the run so far"): the copy is put back to the starting snapshot of the step it stopped on (a `before-so-far` snapshot taken first), so only the steps it passed land, with their ticks; a refused land puts the run back stopped as it was. A run's step is done when its run landed and wasn't undone.
- **The process.** `--on` runs in its own session and goes step to step until a stop; a Grok research stage is waited on as route's Terminal wait does, and taken over when overdue. A process that ends is a process-ended stop. Nothing starts or restarts a run but the owner (see NOT in v2).
- **Unchanged:** who does what (a step's team and its models; a check never by the doer's agent; takeovers and resumes); one step at a time. Auto never runs a project's program and never lands in the folder by itself.
- **Records.** Log version 21: the run row (`mode` `auto`), its steps, the marks, the budget and the calls used. `waiting_on: auto`; reason codes `auto_refused` and `budget`; `--source ui` from the page.
- On the page: see Interface. Built by brief 34.
